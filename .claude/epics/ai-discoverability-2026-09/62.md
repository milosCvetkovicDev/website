# Task: A read-only MCP server so agents can call the site

## Description

An agent can read this site only by fetching pages; there is no way to ask it a question. This task adds one:
a read-only Model Context Protocol server at `/mcp`, answering three tools over the same serialised data the
JSON representation already serves, so "what has this person shipped with Azure?" is one call rather than a
scrape. Be blunt about who will use it: **almost nobody, for its data**. Nothing auto-discovers an MCP server
— SEP-2127 server cards were still an open pull request on 2026-09-11, the competing IETF draft for `mcp://`
plus `/.well-known/mcp-server` expires 2026-09-25 with no working-group adoption, and the official registry
states it "is not intended to be directly consumed by host applications". The one channel with real reach,
Anthropic's Connectors Directory, needs a Team or Enterprise organisation, which this owner does not have.
Realistic consumption is a human pasting a URL into a config file, so the honest case for building it is that
it demonstrates the owner's engineering: spec revision 2026-07-28 is stateless — no `initialize` handshake, no
`Mcp-Session-Id`, therefore no session store and no Redis — and a correct, tested, streamable-HTTP-only server
on the owner's own apex domain is a stronger credential than a sentence claiming MCP experience. It is also
this repository's first and only permitted server function, and the build-output gate from #55 is what
proves no page route followed it.

Branch: feat/mcp-server. Lands as 1 PR, squash-merged.

## Measures

### A read-only MCP server at `/mcp` on spec revision 2026-07-28

- **What:** one route handler at `apps/web/src/app/mcp/route.ts` exporting `POST` only, built on
  `mcp-handler@^2` with `@modelcontextprotocol/server@^2` and `zod@^4`. Stateless: no `initialize` handshake,
  no `Mcp-Session-Id` read or written, no session store, no Redis. The mandatory `server/discover` RPC
  advertises the supported protocol versions, capabilities and identity. `Origin` is validated and a
  present-but-unknown value gets 403; `GET` is not exported, so Next answers 405, which is what the transport
  section asks for; there is no `/sse` and no `/message` route, because the HTTP+SSE transport is formally
  Deprecated.
- **Consumed by:** config-file clients, and only after a human pastes the URL — Claude Code
  (`claude mcp add --transport http`), Claude.ai and Claude Desktop custom connectors in "No sign-in" mode,
  Cursor, VS Code. **Nothing discovers it automatically**, and no directory will list it: the Connectors
  Directory submission portal is organisation-settings-only (Team or Enterprise).
- **Evidence:** formal-standard for the protocol itself — MCP specification revision 2026-07-28 and its
  changelog, fetched 2026-09-12 — and vendor-documented that an unauthenticated read-only server is an
  accepted mode in exactly those clients (Claude remote-connector docs, fetched 2026-09-12). **Speculative for
  any reach whatsoever.** The reason it is worth building is that it demonstrates the owner's engineering, and
  the ADR states that in those words rather than implying a discoverability benefit.
- **Done when:** `POST /mcp` answers `server/discover` and `tools/list` for protocol `2026-07-28` with no
  `Mcp-Session-Id` in the response headers; `GET /mcp` is 405; `/sse` and `/message` are 404; a bogus `Origin`
  is 403; an `MCP-Protocol-Version` that disagrees with the body `_meta` is 400 with JSON-RPC `-32020`.

### Three read-only tools over the serialisation #60 already ships

- **What:** `search_case_studies({ query })` over titles, tags, highlights and tech stacks;
  `get_case_study({ slug })`; and `get_tech_stack()`, the union of every `techStack` category with the slugs
  each item appears in. Each tool carries a `title` and `readOnlyHint: true`; `tools/list` results carry
  `ttlMs` and `cacheScope`, which the 2026-07-28 revision requires because list results no longer vary per
  connection. Payloads come from the serialiser #59 lands and #60 already reuses — no second
  serialisation path, no fact written twice. No write tool, and no `listChanged` or `subscriptions/listen`
  capability is advertised.
- **Consumed by:** the same config-file clients, once attached — the tools are the only thing they can call.
  Nothing else reads them: MCP clients do not consult `robots.txt`, and no crawler speaks JSON-RPC.
- **Evidence:** formal-standard for `ttlMs`/`cacheScope` and the stateless list semantics (2026-07-28
  changelog, fetched 2026-09-12); vendor-documented for the annotations — Anthropic's directory submission
  requires every tool to have a `title` and the applicable `readOnlyHint`/`destructiveHint` (fetched
  2026-09-12), and OpenAI's review rules say the same; convention-only for the tool set itself, whose live
  precedent is `resumes.md`'s public, unauthenticated, read-only server with four list/get/search tools
  (fetched 2026-09-12).
- **Done when:** a unit test deep-equals each tool payload against the same serialiser call the JSON
  representation makes, so a change to one cannot leave the other behind; every slug in `caseStudies` is
  reachable through `get_case_study`; an unknown slug returns an error _result_ rather than throwing; and no
  tool returns less than the corresponding page's served HTML already says.

## Technical Details

**The handler.** `apps/web/src/app/mcp/route.ts` exports `POST` only, wrapping `createMcpHandler` from
`mcp-handler@^2`. Tool definitions live beside it in `apps/web/src/app/mcp/tools.ts` so they are unit-testable
without booting a server, registered with the v2 `server.registerTool(name, { title, description,
inputSchema, annotations }, fn)` form. **Do not copy Vercel's own MCP deployment page** (last updated
2026-08-31): its sample is still 1.x-shaped — `server.tool(name, desc, schema, fn)`, a `{ basePath: '/api' }`
argument and `export { handler as GET, handler as POST, handler as DELETE }` — which would ship a 2025-era
server with a session header and a GET stream. Use the package's own v2 README. Data comes from the serialiser
#59 lands and #60 already reuses, which in turn reads `caseStudies`
(`apps/web/src/data/case-studies.ts:43`), `getCaseStudy` (`:170`), `formatMetric` (`:21`) and the `CaseStudy`
interface (`:27`) plus #56's date and metric-definition fields. Answers are O(1) reads of a compiled-in
constant with no I/O, so there is nothing to make the handler slow and nothing that can fail at runtime except
the handler itself.

**Mount at `/mcp`, not `/api/mcp`.** `apps/web/src/app/robots.ts:10` disallows `/api/`. MCP clients ignore
`robots.txt`, so `/api/mcp` would work for agents — but `/mcp` is the conventional shape OpenAI's docs assume
("a stable URL, typically ending in /mcp"), and keeping this epic's crawlable JSON out of `/api/` is the same
decision. `robots.ts` is task #48's file and is not touched here. `/mcp` is also deliberately **not** added to
`sitemap.ts` or to any `alternates` block: a POST-only JSON-RPC endpoint has nothing to index, and a crawler's
GET correctly gets 405.

**Next.js 16 specifics, with the trap named.** Route handlers are **not** static by default: since Next
15.0.0-RC a `GET` with no `dynamic` export becomes a function, which is why every _content_ endpoint in this
epic carries `export const dynamic = 'force-static'` and why one missing line silently costs the static
posture. `/mcp` is the single deliberate exception — a `POST` handler cannot be prerendered, so it is a
function by construction, and that is what makes the gate's allowlist exactly one entry long rather than zero.
Two further facts matter at implementation time: `force-static` is removed **only when `cacheComponents` is
enabled**, and `apps/web/next.config.ts:33-43` sets no such flag (it sets `turbopack.root` and `distDir` and
nothing else), so `force-static` is the correct mechanism today and the sibling endpoints would need
`'use cache'` instead if Cache Components were ever adopted — `/mcp` would be unaffected either way. And
`[slug].md` cannot work: Next types a partial dynamic segment as a literal with zero params
(`RouteHandlerConfig<"/work/[slug].md">` with `params: Promise<{}>`, a typecheck failure reproduced in this
repository on 2026-09-12), so the tool payloads address a case study by its real URLs — `/work/<slug>` and the
`/work/<slug>/index.md` twin #59 lands — and never invent a `/work/<slug>.md` that cannot exist.

**Required wire details (2026-07-28).** Every POST carries `MCP-Protocol-Version` matching the body `_meta`
(`io.modelcontextprotocol/protocolVersion`, alongside `clientInfo` and `clientCapabilities`), plus `Mcp-Method`
and, for `tools/call`, `Mcp-Name`; a mismatch is 400 with `-32020`. `Origin` validation is a MUST with 403 on
an invalid value, and a permissive `Access-Control-Allow-Origin: *` without it is the DNS-rebinding footgun the
spec calls out. `tools/list` results must carry `ttlMs` and `cacheScope`. The SDK implements `server/discover`,
the header checks and the error codes; the tests assert them rather than trusting them. A shaped smoke call:

```bash
curl -sS -X POST https://miloscvetkovic.dev/mcp \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -H 'MCP-Protocol-Version: 2026-07-28' \
  -H 'Mcp-Method: tools/list' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{},
       "_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28"}}'
```

**Vercel function configuration.** This is the deployment's first and only function. Fluid compute is the
recommended compute model for an MCP endpoint's idle-then-burst shape and is on by default. **Do not add a
`vercel.json` `maxDuration`**: on Hobby 300s is both the default and the maximum, so the setting has no
effect; there is no `vercel.json` in this repository and this task does not add one. The other Hobby limits —
single region, 2 GB / 1 vCPU, a 4.5 MB body cap, 30,000 concurrency — are orders of magnitude away from a
handler answering from a constant. Two real exposures: the endpoint is unmetered public compute on a plan with
no spend cap (the widely-quoted 1M invocations/month figure comes from secondary summaries, not Vercel's
pricing page — confirm it in the dashboard), and any bot-challenge or AI-bot ruleset must **exclude** `/mcp`,
because a JavaScript challenge breaks every MCP client. The owner's recorded crawler decision is full
openness, so no blocking ruleset is planned in the first place; a Firewall rate-limit rule on `/mcp` is a
dashboard action, outside this repository. Hobby is also explicitly non-commercial, which is worth a conscious
acknowledgement for a site that markets consulting work. No `.vercelignore` change is needed — nothing new is
generated outside `.next`.

**Dependencies.** `mcp-handler@^2`, `@modelcontextprotocol/server@^2` and `zod@^4` are the first runtime
dependencies `apps/web` has gained beyond the five at `apps/web/package.json:17-23`, and the first server-side
ones in the repository. Add them through pnpm. Expect a larger `pnpm-lock.yaml` diff than three lines, because
the first `pnpm add` in a worktree rewrites resolved peer suffixes, and expect to work the documented
`allowBuilds` procedure if `pnpm install` reports a new ignored build script: `pnpm ignored-builds`,
`pnpm why -r <name>`, read the script, then add a `true`/`false` entry with a `Reviewed at <version>` comment
(ADR 0013). `pnpm check:allowbuilds` fails closed, so an unrecognised edit to that block fails CI.

**Tests.** Unit tests go in `apps/web/src/app/mcp/__tests__/` with `@vitest-environment node` in a docblock,
following the three files in `apps/web/src/data/__tests__/`: a jsdom window costs about two seconds per file
and there is no DOM here. The e2e spec uses Playwright's `request` fixture, so it opens no page and touches
neither the console nor the axe gate; it keeps default retries (only `console-clean.spec.ts` and
`accessibility.spec.ts` set `retries: 0`, and those overrides stay). Playwright owns its server on port 3210
locally (ADR 0014), so the spec must not assume port 3000. Preview deployments redirect to a Vercel login, so
the post-merge `claude mcp add` check runs against production; on the Hobby plan a busy merge day can exhaust
the daily deployment allowance, so allow for the deploy to be queued (`docs/runbooks/deploy.md`).

**What this consumes from epic #42 rather than reimplementing.**

- **#48** — the canonical/base-URL and metadata helpers. The snippet module and the tool payloads read the
  site origin from #48's helper; this task adds no second origin constant and does not touch `robots.ts`,
  `sitemap.ts`, icons, headers or `serializeJsonLd`. No JSON-LD is added here: there is no schema.org type for
  an MCP endpoint and none is invented.
- **#43** — the served-response test pattern and `apps/web/e2e/routes.ts`. `e2e/mcp.spec.ts` asserts on the
  response, not the hydrated DOM, in that style. `/mcp` is deliberately **not** added to the route list: it is
  not a page and answers only POST, so the console, axe and text-floor walks must not visit it.
- **#47** — the per-character span fix. Nothing here depends on it: the tools return data objects and bypass
  the HTML entirely. The extraction path for shattered headings is #59's Markdown twins, not this task,
  and this task must not be described as fixing it.
- **#49** — the metric contradictions. The tools serialise metrics through `formatMetric` and #56's
  scope-and-window fields, so whatever #49 corrects in the numbers flows through with no second copy.

**Deliberately not done in this area, with evidence.**

- **An MCP Apps widget** (`io.modelcontextprotocol/ui`) — PRD Out of Scope and the owner's explicit decision.
  Extensions are disabled by default on both sides (MCP extensions overview, fetched 2026-09-12), the audience
  is the same near-zero set as the base server, and it would add a second rendering surface with its own CSP
  and reduced-motion story that the existing axe and console gates cannot see.
- **WebMCP / `document.modelContext`** — PRD Out of Scope. It is a Draft Community Group Report dated
  2026-09-10, "not a W3C Standard nor is it on the W3C Standards Track", in a Chrome origin trial, and
  mainstream agents do not call WebMCP tools. Honest consequence: Lighthouse's three `webmcp-*` audits stay
  `notApplicable`, so shipping `/mcp` moves no Lighthouse number — which is also why #55 asserts audit
  ids and never the `agentic-browsing` category score.
- **`/.well-known/mcp.json`, `.well-known/mcp/server-cards.json`, `/.well-known/mcp-server`, `_mcp.<domain>`
  TXT** — nothing reads any of them. SEP-2127 was an open pull request on 2026-09-11 with its path still under
  discussion; `draft-serra-mcp-discovery-uri-04` has "no formal standing in the IETF standards process" and
  expires 2026-09-25. The shipped in-protocol discovery is `server/discover`, which presupposes the URL.
- **`/.well-known/ai-plugin.json`** — PRD Out of Scope; new plugin conversations were blocked 2024-03-19 and
  all plugin chats shut down 2024-04-09, and OpenAI's current plugin documentation never mentions it.
- **`agents.json`** — PRD Out of Scope; version 0.1.0, no evidence of consumption, and a "list then read"
  content model has no multi-step flows for it to describe.
- **OAuth, `withMcpAuth`, `/.well-known/oauth-protected-resource`** — authorization is OPTIONAL in the spec
  and the clients that matter accept a no-sign-in server. Skipping it is a knowing deviation from the
  transport section's SHOULD, recorded in the ADR, not an oversight.
- **`/sse`, `/message`, `Mcp-Session-Id` handling, Redis or any session store** — the HTTP+SSE transport is
  formally Deprecated and protocol-level sessions were removed in 2026-07-28; `mcp-handler@2.0.0` answers
  `410 Gone` on those paths.
- **Any write tool** (contact or brief submission over MCP) — an unauthenticated endpoint has no audit trail,
  so a write tool is a spam vector, and both review programmes hinge on accurate `destructiveHint`. Read-only.
- **`listChanged` / `subscriptions/listen`** — a Hobby function is killed at 300s, and cacheable `ttlMs` list
  results are what the 2026-07-28 revision asks for anyway.
- **Anthropic Connectors Directory and OpenAI plugins-directory submission** — the former's portal requires a
  Team or Enterprise organisation ("Organization settings aren't available on individual plans", fetched
  2026-09-12); the latter requires verified individual or business identity, a passing tool scan and a
  `/.well-known/openai-apps-challenge` domain proof. Neither is attempted; the ADR says why.
- **Publishing to the official MCP Registry** — not part of this task. The registry is in preview with
  possible data resets and states host applications should not consume it directly; a `dev.miloscvetkovic/*`
  namespace needs a DNS TXT record at the apex or an extensionless `.well-known/mcp-registry-auth` file whose
  served content type is unverified. Recorded in the ADR as an optional owner follow-up.

**Owner decisions that apply** (recorded 2026-09-12): a read-only, unauthenticated MCP server at `/mcp`
against spec revision 2026-07-28, stateless, with copy-paste connector snippets, and no MCP Apps widget; Tier
4 is limited to this server; full crawler openness, training included, so nothing that could challenge `/mcp`
is configured; Claude drafts and the owner edits anything in their voice, which here means the tool
`description` strings and the `/contact` prose. Nothing in this task needs a fabricated value: every payload

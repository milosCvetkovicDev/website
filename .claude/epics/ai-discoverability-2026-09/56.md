# Task: Give the content real dates and honest metric definitions

## Description

A machine reading this site cannot learn when anything happened or what any number means. No route carries a
date — not visible, not in markup, not in a feed — so there is no freshness signal for any engine, nothing true
for a sitemap `lastmod` to hold (#48 strips the build-time stamp precisely because there is nothing honest to
put there), and `Article` markup is impossible because its recommended date properties have no source. And every
metric is a bare number: `apps/web/src/data/case-studies.ts:49` defines the headline figure as
`{ value: 73, suffix: '%', label: 'faster resolution' }` with no measurement window and no method, which is
both the shape a reader cannot verify and the shape the GEO benchmark found least effective. #49 supplies the
other missing half — a one-line `basis` on `CaseStudyMetric`, what was measured against what baseline — so
this task adds only what #49 does not carry and restates none of it.
This task extends the `CaseStudy` interface with a `dates` field and a `metricDefinition` field holding the
measurement window and the method, both shaped as discriminated unions over one sentinel so the compiler
forces every consumer to handle the not-yet-filled case; seeds them with registered placeholders so the
machinery merges before the owner's real values exist; ships the epic's single placeholder marker and the gate
that fails and names the field while a placeholder is unregistered or past its owner-chosen deadline, over
every source a later task registers with it — #58's page copy, #60's generated strings, #61's
`posts.ts` — renders the dates visibly on the case-study pages, because Google's structured-data policies
forbid asserting in markup what the page does not show; and restores the sitemap's `lastmod` for case-study
URLs from the new data.
It lands the data half of FR-6 and FR-7 only: the `Article` markup that consumes the dates is #57, and
the one visible sentence joining #49's basis to this task's window and method is #58's, composed by this
task's `formatMetricScope` so neither fact is written twice.

Branch: feat/case-study-dates-and-metrics. Lands as one PR, squash-merged.

## Measures

### Dates in the content model, rendered visibly on each case study

- **What:** add `dates` to `interface CaseStudy` as
  `{ state: 'dated'; datePublished: string; dateModified: string } | { state: typeof OWNER_TODO }`, with both
  values accepted only as `YYYY-MM-DD` or a full ISO 8601 timestamp carrying an explicit offset. Render a
  labelled, visible `Published` / `Updated` line in the header of `apps/web/src/app/work/[slug]/page.tsx`, each
  as `<time dateTime="…">` whose attribute is the stored value byte for byte. A study whose `dates` are still
  unfilled renders no date block at all rather than an empty or invented one.
- **Consumed by:** Google Search — the `Article` rich result's recommended `datePublished`/`dateModified`
  (emitted by #57, which cannot exist without this field) and Google's publication-dates guidance, which
  requires the visible and marked-up dates to agree. Microsoft/Bing for freshness. Human readers, who are the
  audience that actually hires. And this repository's own sitemap.
- **Evidence:** vendor-documented — Google's `Article` reference (developers.google.com, last updated
  2026-09-08) lists `datePublished`/`dateModified` as recommended and `Article` is one of the 31 features in
  Google's current structured-data gallery (verified 2026-06-15); Google's publication-dates guidance
  (developers.google.com, last updated 2025-12-10) requires a prominent, labelled, user-visible date matching
  the markup and forbids future dates; Microsoft's Bing Webmaster AI Performance announcement (2026-02-10)
  states that regular updates help AI systems reference the most current version of content. That dates drive
  answer-engine _citation_ specifically is convention-only: the reported claim that one engine weights content
  under 30 days far more heavily is unverified SEO-industry reporting and this task does not assert it, and
  Google states in its AI-optimization guide (2026-07-10) that structured data is not required for generative
  AI search at all.
- **Done when:** each case study with filled dates shows `Published` and `Updated` in the served HTML with
  `<time dateTime>` equal to the stored value, each unfilled one shows neither, and no route's response body
  contains the sentinel string.

### The `OWNER-TODO` sentinel, the typed placeholder and the dated register gate

- **What:** a new `apps/web/src/data/owner-todo.ts` — the epic's one placeholder convention, and the reason
  every other task in it can register a placeholder instead of inventing a second spelling. It exports
  `OWNER_TODO = 'OWNER-TODO'`; the marker helper `ownerTodo(hint: string)`, returning
  `OWNER-TODO(<hint>)`, so a marker embedded in a drafted sentence carries what the owner must supply and
  still contains the one literal; the register
  `unfilledOwnerFields: { field: string; why: string; expires: string }[]`; and a pure checker
  `findOwnerTodoProblems(sources, register, now)` returning one finding per problem. A source is
  `{ id: string; value: unknown }` whose `value` is walked recursively, and a field counts as unfilled either
  because a discriminated union's `state === OWNER_TODO` or because a string anywhere inside it contains the
  literal `OWNER-TODO` — so a bare generated string is as much a source as a data module is. The checker
  reports three classes: an unfilled field absent from the register; a register row matching no unfilled field
  (stale, so the owner's value has landed and the row must go); and a row whose `expires` is missing, is
  itself the sentinel, or is on or before `now`. `pnpm test` runs it over every registered source and fails
  naming `<source>.<path>`; the command the sibling tasks cite for this gate is
  `pnpm --filter web exec vitest run src/data/__tests__/owner-todo.test.ts`. Two rules travel with the module
  and bind every task that uses it. **One spelling:** markers come from `ownerTodo(...)` and are never
  hand-typed, so #58's drafted `[[owner: …]]` placeholders, #60's blockquote and ground-truth block
  and #61's `posts.ts` fields all carry this one form and one gate catches all of them. **One publication
  rule:** a marker never reaches served output — the consumer omits the whole sentence, row or block while its
  marker survives, exactly as an undated study renders no date block, and the register's `expires` is what
  stops that omission from becoming permanent.
- **Consumed by:** nothing outside this repository reads it. It exists so that a placeholder cannot be
  forgotten and cannot be published, and so this task's machinery can merge before the owner has supplied a
  single real value.
- **Evidence:** convention-only, and the honest reason is twofold: it enforces the PRD's "nothing fabricated"
  non-functional requirement mechanically rather than by good intentions, and it demonstrates the owner's
  engineering — a known-gap register with an owner-set expiry, mirroring the `allowBuilds` /
  `Reviewed at <version>` / `pnpm check:allowbuilds` drift pattern this repository already runs (ADR 0013).
- **Done when:** the checker has unit coverage for all three failure classes plus the clean case, exercised
  over both detection modes and over two source kinds (a nested data module and a bare generated string); a
  registered in-date placeholder keeps CI green; and removing a register row or moving `expires` into the past
  turns `pnpm --filter web exec vitest run src/data/__tests__/owner-todo.test.ts` red with `<source>.<path>`
  named in the message.

### A measurement window and a method, joined to #49's basis line by one helper

- **What:** add `metricDefinition` to `interface CaseStudy` as
  `{ state: 'defined'; window: { from: string; to: string }; method: string } | { state: typeof OWNER_TODO }`.
  `window` is the closed measurement interval as two ISO dates and `method` says how the number was produced.
  What the number counted and what it is a fraction of is deliberately **not** here: that is the one-line
  `basis` #49 adds to `CaseStudyMetric`, and this task reads it rather than restating it, so each fact keeps
  exactly one home. `formatMetricScope(basis: string | null, definition: MetricDefinition)` is the single
  producer of the sentence that joins them — #49's basis first, then this window and method — and #58
  renders its output rather than re-deriving anything. It takes the basis as a parameter instead of reading
  `CaseStudyMetric`, so it depends on nothing about the shape #49 gives that interface and needs no rewrite in
  either merge order: with #49 merged the call site passes `study.highlight.metric.basis`, and before that it
  passes `null` and the sentence is the window-and-method half alone. The field sits on `CaseStudy`,
  deliberately not inside `CaseStudyMetric`.
- **Consumed by:** generative engines, per benchmark rather than per vendor statement; human readers; task
  #58's one visible line; and the serialiser of #59, #60 and #62. All of them read `formatMetricScope`'s
  output or the two fields behind it, never a second copy of #49's basis. Nothing consumes it as markup —
  Google states no schema is needed for generative AI search, and the definition is plain visible prose by
  design.
- **Evidence:** measured, but in an academic benchmark, not a vendor statement — the KDD 2024 GEO paper
  (arXiv:2311.09735, revised 2024-06-28) reports Statistics Addition +37% and Cite Sources +30% relative
  visibility in generative engines, with Keyword Stuffing at −9%; the 2026 follow-ups (arXiv:2603.09296,
  arXiv:2604.19113) agree in direction without per-feature numbers. Treat the direction as supported and the
  magnitude as unknown: the paper predates every 2026 engine version.
- **Done when:** the type exists; `formatMetricScope` is total (the joined sentence, #49's basis unchanged
  while only the definition is unfilled, or `null` when there is nothing honest to say — never a partial
  string and never a marker); and the window and method for each headline figure are the owner's or registered
  placeholders, with what the figure means left to #49.

### Sitemap `lastmod` restored from real data, for case-study URLs only

- **What:** `apps/web/src/app/sitemap.ts` sets `lastModified` on a case-study entry only when that study's
  `dates` are filled, taking `dateModified` verbatim. The five remaining static routes keep no `lastModified`:
  nothing in the repository makes an honest content date for them checkable, and a stamp nobody can check is
  what #48 just removed.
- **Consumed by:** Google, Bing and every sitemap-reading crawler.
- **Evidence:** vendor-documented for the mechanism — the sitemaps.org protocol makes `lastmod` optional per
  URL, and Next.js's `sitemap` reference (16.3.5, lastUpdated 2026-08-25) documents `lastModified` accepting an
  ISO string, so it can come from data rather than the clock. The further claim that Google ignores a `lastmod`
  it finds inaccurate is reported rather than documented in the sources this epic gathered, so nothing here
  rests on it beyond the plain fact that a build-time stamp was untrue.
- **Done when:** `/sitemap.xml` carries `<lastmod>` for exactly the case-study URLs whose dates are filled, each
  equal to that study's `dateModified`, and `sitemap()` returns identical output at two different system times.

## Technical Details

### The content model, against the current code

- `apps/web/src/data/case-studies.ts:27-41` is `interface CaseStudy` today: `slug`, `title`, `description`,
  `tags`, `highlight`, `challenge`, `approach`, `contributions`, `impact`, `techStack`. Add two fields to it:
  `dates: CaseStudyDates` and `metricDefinition: MetricDefinition`. All three studies (`:43-168`) get seeded
  entries.
- Both new types are **discriminated unions**, not optional strings, and this is the load-bearing choice. A
  `datePublished: string | 'OWNER-TODO'` collapses to `string` in TypeScript and buys nothing; a union
  discriminated on `state` makes `pnpm typecheck` fail on any consumer that reaches for the value without
  handling the unfilled branch. That is the first of the four layers keeping a placeholder out of production,
  and the only one that works at compile time.
- `metricDefinition` goes on `CaseStudy`, **not** inside `CaseStudyMetric` (`:1-7`), and #49's `basis` stays
  where #49 put it. `CaseStudyMetric` crosses the server/client boundary:
  `apps/web/src/components/featured-work/metric-counter.tsx:7` declares
  `interface MetricCounterProps extends CaseStudyMetric` in a `'use client'` module, and
  `apps/web/src/components/featured-work.tsx:157` renders `<MetricCounter {...project.metric} active={isActive} />`,
  so every field of `CaseStudyMetric` is serialised into the client payload for all three home-page cards.
  Nesting this task's window and method prose there would ship it three times to every visitor of `/` for no
  reader — the client payload discipline ADR 0009 rule 5 exists to protect. The honest cost of the split is
  worth stating: #49's one-line `basis` does ride along in that payload, because #49 chose `CaseStudyMetric`
  for it. That is #49's call on one short string, this task does not move it, and nothing here adds a second
  field to that interface. Keeping `metricDefinition` on `CaseStudy` also leaves
  `apps/web/src/data/featured-projects.ts:4,29` (`FeaturedProject extends CaseStudyHighlight`, built with
  `...study.highlight`) and the six `MetricCounter` literals in
  `apps/web/src/components/featured-work/__tests__/metric-counter.test.tsx` untouched.
- **One fact, one home, one producer.** #49 owns what a number counted and what it is a fraction of, as its
  one-line `basis`; this task owns when it was measured and how, as `metricDefinition`. Neither restates the
  other, which is what the epic's "no fact is written twice" decision requires, and `formatMetricScope` is the
  only place the two are joined into a sentence. Task #58 renders that sentence; #59, #60 and #62
  serialise either it or the two fields behind it. The alternative — `metricDefinition` subsuming `basis` and
  #49's field being deleted — was rejected for two reasons: it would rewrite a decision of another epic's
  issue, and because `metricDefinition` is one all-or-nothing union, an unfilled window would take the basis
  line off the page with it, regressing what #49 shipped.
- `formatMetric` (`:21-25`) is not changed. `formatMetricScope(basis, definition)` and
  `formatPublicationDates(dates)` are new exports beside it, both total in the same spirit as `formatMetric`'s
  em-dash fallback: they return `null` rather than a half-built string, and `formatMetricScope` returns the
  basis unchanged when only the window and method are missing.
- Accepted date grammar: `YYYY-MM-DD`, or a full ISO 8601 timestamp with an explicit `Z` or ±HH:MM offset. A
  timestamp with no offset is rejected, because the build machine's timezone would silently resolve it and the
  value is then frozen into prerendered HTML. This is also why the visible string must not be produced by a
  bare `toLocaleDateString()`: the output is baked at build time, so a change of build environment would
  silently change published text. Use a fixed month table, or `Intl` with an explicit locale and
  `timeZone: 'UTC'`, and pin the exact string in a unit test. (A locale-dependent format is additionally a
  hydration hazard, but only if the formatting ever moves into a client component — server component output is
  not re-rendered on the client, so keep the formatting on the server and the hazard never arises.)

### The placeholder gate: how the machinery merges and how a placeholder cannot ship

Four layers, each doing one job:

1. **The type** forbids reading an unfilled value without narrowing (`pnpm typecheck`). This layer covers the
   typed placeholders only; a marker embedded in a sentence is a plain string and is caught by layers 3 and 4.
2. **The renderers** are total: `formatPublicationDates` returns `null`, and
   `apps/web/src/app/work/[slug]/page.tsx` renders no date block for `null`. There is no code path that prints
   the sentinel. The same rule binds every later task that registers a marker — omit the sentence, the row or
   the block while its marker survives, never print a half-filled one.
3. **The served-HTML assertion** greps every route body and `/sitemap.xml` for `OWNER-TODO` (AC 8), so a future
   edit that does find a path to print it fails the `e2e` job. Because `ownerTodo(...)` composes its marker
   around that same literal, one grep covers both placeholder forms.
4. **The register with an owner-set deadline** stops a placeholder from living forever. `unfilledOwnerFields`
   lists each unfilled field with `why` and `expires`; `findOwnerTodoProblems` fails on an unregistered
   unfilled field, on a stale row, and on an `expires` that is missing, is the sentinel, or has passed.

**One convention for the whole epic, and how a sibling task joins it.** Four tasks register placeholders in
four different shapes, so the checker takes sources rather than case studies: `{ id, value }` pairs whose
`value` it walks. The source list lives in `apps/web/src/data/__tests__/owner-todo.test.ts` as one array
literal, and joining the gate is one entry in it plus one register row per field:

- **#56** (this task) — `{ id: 'case-studies', value: caseStudies }`, covering `dates` and
  `metricDefinition` and, for free, any string in that module carrying the literal — #49's `basis` included,
  since the walk finds strings without being told the field names.
- **#58** — the `/about` quick-fact records, the `/skills` self-assessment note and the availability
  answer, whose drafts are written with `ownerTodo(...)` in place of `[[owner: …]]`.
- **#60** — one entry whose `value` is the body its `/llms.txt` builder returns, covering the drafted
  blockquote and the ground-truth block. A generated artifact is a function's output, so only a test can hand it
  to the checker; that is why this gate lives in Vitest and why #60's demonstration runs
  `pnpm --filter web exec vitest run src/data/__tests__/owner-todo.test.ts` rather than a `scripts/` command
  that has no way to render it.
- **#61** — `{ id: 'posts', value: posts }` for the drafted posts' dates and fields.

`owner-todo.ts` imports nothing from `src/data`, so the register never cycles back into the modules it
describes, and the walk names `<source>.<path>` whatever a later task registers.

The merge story follows from layer 4: the PR is mergeable as soon as the owner names a date by which they will
supply the real values, which is a decision no agent can fabricate and which takes the owner seconds. The
sentinel value for `expires` is treated as already expired, so the owner cannot be skipped. This task file
deliberately picks no date. Note for the sibling tasks that demonstrate the gate: a **registered, in-date**
marker is green by design — that is what lets machinery merge ahead of the owner's words — so the non-zero run
to paste is the one with the register row removed or its `expires` in the past, and the zero run is the one
after the owner's text lands.

The consequence is real and should be stated in the PR: once a deadline passes, `pnpm test` is red for every
branch, not just this one, until the owner fills the value or consciously moves the date in a PR. That pressure
is the point, and it is why the deadline is the owner's own. Do not neutralise it by freezing the clock in the
live-data test — the format, ordering and future-date assertions use `vi.setSystemTime` for determinism, and the
expiry check deliberately does not.

Why this gate is a Vitest test rather than a new `scripts/*.mjs` beside `scripts/check-allowbuilds-drift.mjs`:
the data is a TypeScript module, and Vitest already imports it under `@vitest-environment node`
(`apps/web/src/data/__tests__/case-studies.test.ts:1-9`), so the check walks real exported values and names
`<source>.<path>` exactly instead of text-scanning source — which would miss a marker composed at runtime, as
#60's generated body is, and would flag the one module that legitimately spells the literal out.
`pnpm test:scripts` and its glob stay untouched; the gate lands in the `quality` job through `pnpm test`, as
the PRD requires of offline gates. Task #61's acceptance criterion allows for either home and names the Vitest
command when the gate lands here, which it does.

### Next.js 16 specifics that bind this task

- **This task adds no route handler.** `sitemap.ts` is a metadata route and stays prerendered; the build-output
  assertion (AC 15) is there because its new data import is exactly the kind of change that could move a route
  into the `ƒ` column silently — the endpoint would still work, it would just stop being static.
- **Route handlers are not static by default.** Since Next 15.0.0-RC the default caching for `GET` handlers is
  dynamic, so a `route.ts` without `export const dynamic = 'force-static'` becomes a serverless function. This
  was measured in this repository on next 16.3.4 (2026-09-12): the same probe built `○ /llms.txt` with the
  export and `ƒ /llms-full.txt` without it. One missing line is the whole difference. It binds #59, #60,
  #61 and #62, which do add handlers; the `/mcp` endpoint of #62 is the single permitted function.
- **`force-static` is removed only when `cacheComponents` is enabled** (Next 16.0.0 removed `dynamic`,
  `dynamicParams`, `revalidate` and `fetchCache` under Cache Components). This repository does not set
  `cacheComponents`, so the export is valid today; the option now lives in the "Caching (Previous Model)" guide,
  which reads like deprecation and is easy to misread as removal.

- **No second basis field, and no restatement of #49's line.** What a number counted and what it is a fraction
  of is written once, in the `basis` #49 adds to `CaseStudyMetric`; `metricDefinition` carries only the window
  and the method, and `formatMetricScope` is the single place the two meet. Nothing here adds a field to
  `CaseStudyMetric`, edits `basis`, or renders a second scope line.
- **No second placeholder convention.** One sentinel, one `ownerTodo(...)` marker spelling, one register, one
  checker taking sources, one command — #58, #60 and #61 extend this gate instead of adding theirs, which
  is why the checker takes `{ id, value }` sources rather than case studies.
- **No `Article` or `TechArticle` JSON-LD here** — that is #57, and emitting it before the dates exist
  would mark up values the page does not show, which Google's structured-data policies forbid.
- **No per-route dates for `/`, `/about`, `/skills`, `/contact` and no `src/data/pages.ts`.** Nothing in the
  repository makes a content date for those checkable, so a hand-maintained value would rot into the same
  untrue stamp #48 just removed. Deriving one from `git log -1 --format=%cI -- <path>` was considered and
  rejected: whether the deployment build's clone carries enough history is unverified, and it would date a
  route by its last code change rather than its last content change.
- **No `FAQPage`, no `HowTo`, no `speakable`, no `SearchAction`.** All refused for the whole epic with evidence:
  Google's FAQ rich result stopped appearing 2026-05-07 and the documentation was deleted 2026-06-15; `HowTo`
  documentation was removed 2023-09-14; the sitelinks search box was retired globally 2024-11-21. Task #63's
  ADR records these with their dates.
- **No `llms-full.txt`, `ai.txt`, TDMRep, Content-Signals, `ai-plugin.json`, `agents.json`, JSON Resume,
  WebMCP, `/.well-known/agent-skills`, IndexNow or a self-created Wikidata item.** Settled in the PRD's Out of
  Scope list; a date field is not a reason to reopen any of them.
- **No backdating and no `dateModified` churn.** A date is moved only when the content actually changed, in the
  same PR as the change. Google's date guidance treats inconsistent dates as a defect, and a portfolio whose
  three pages all "updated" on every deploy is the pattern that makes the field worthless.
- **No claim that dates or markup produce AI citations.** Google states structured data is not required for
  generative AI search (2026-07-10) and Ahrefs' matched difference-in-differences over 1,885 pages found no
  citation lift from adding JSON-LD (2026-05-11). The dates are here for a live Google rich result, a
  vendor-stated freshness signal, an honest sitemap, and human readers.

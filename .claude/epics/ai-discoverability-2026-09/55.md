# Task: Measurement baseline and the gates this surface needs

## Description

Nothing this epic proposes is provable today, and the existing measurements actively mislead. Lighthouse
13.4.1 scores this site's `agentic-browsing` category **1.0** with four of its six audits
`notApplicable`, and scores SEO **100** while not one of the nine routes carries a
`<link rel="canonical">` — because the `canonical` audit returns `notApplicable` when the tag is absent
instead of failing. A gate built on either category score would have certified every gap in the PRD as
fine. This task replaces category scores with named-audit assertions, adds the four things no existing
gate can see (text that survives a non-rendering crawler, a build output free of accidental serverless
functions, a `robots.txt` that does not block the site's own CSS and JS, and structured data validated
offline), and captures the one piece of evidence that cannot be recreated later: a dated first-party
baseline in Google Search Console and Bing Webmaster Tools, three days after the site went live on
2026-09-09. It also lands the endpoint tests for #59, #60 and #62 as declared expected failures,
so each of those tasks has a red test naming it before a line of it is written.

Branch: `test/ai-discoverability-gates`, with the dated baseline record on
`docs/ai-discoverability-baseline`. Lands as 2 PRs, squash-merged.

### A no-JavaScript served-HTML text spec: per-route floor plus load-bearing phrases

- **What:** a Playwright spec that fetches each route with `request.get(path)` — the response body, not
  the hydrated DOM — strips `script`/`style` and tags with a **zero-join** extractor, and asserts per
  route: HTTP 200, a character floor, the presence of that route's load-bearing phrases, and that the
  JavaScript-enabled `innerText` is not more than 15% larger than the static text (which catches the
  day copy moves into a client-only component).
- **Consumed by:** every dedicated AI crawler, directly — GPTBot, OAI-SearchBot, ChatGPT-User,
  ClaudeBot, Claude-User, Claude-SearchBot, PerplexityBot and Bytespider read exactly these bytes.
  Googlebot and Applebot are the only two crawlers that document a renderer, and no crawler scrolls,
  so scroll-triggered content is invisible even to those two.
- **Evidence:** measured, with one stale link in the chain. The crawler behaviour comes from the only
  primary measurement, Vercel/MERJ over ~1.3bn fetches
  (`vercel.com/blog/the-rise-of-the-ai-crawler`, 2024-12-17) — 21 months old, and no vendor has
  documented rendering either way since, so treat it as widely believed rather than freshly verified.
  This site's own numbers are from 2026-09-12: a `curl` of `/` returned 148,754 bytes and 5,156
  characters of extractable body text with every story phase present, a `javaScriptEnabled: false`
  Playwright fetch returned HTML of essentially identical size, and the rendered `innerText` was 5,320
  characters — a 3% difference. A second researcher's extractor measured 4,623 characters on the same
  page the same day, which is why the spec pins its extraction function instead of trusting a number.
- **Done when:** the spec passes in both e2e modes with floors and phrases derived from a measurement
  taken during implementation, and the measurement's date is in the spec's docblock.

### A build-output gate: the deployment stays function-free

- **What:** a `node:test`-shaped script at `scripts/check-build-output.mjs`, run as
  `pnpm check:build-output` after the existing `Build` step in the `quality` job. It asserts against
  the emitted artifacts under `apps/web/.next/server/app/` — not the terminal table — that every page
  route has a prerendered body, and that the set of routes requiring per-request compute is exactly
  the explicit allowlist, which is **empty today** and gains `/mcp` and nothing else in #62.
- **Consumed by:** nothing external. This is the stop condition that protects the epic's hardest
  constraint, and the failure it catches is silent: a route handler missing
  `export const dynamic = 'force-static'` still serves the right bytes, it just costs an invocation per
  crawl on a Hobby plan this project has already hit deploy limits on.
- **Evidence:** measured in this repository on 2026-09-12. A probe added two handlers at Next 16.3.4:
  the one with `force-static` built as `○ /llms.txt`, the one without it built as `ƒ /llms-full.txt`,
  and every other route was untouched. The same probe recorded a clean-tree baseline of 15 route-table
  entries, all `○` or `●`, zero `ƒ`.
- **Done when:** `pnpm check:build-output` exits 0 on a clean tree, exits non-zero when an expected
  body is missing or an unlisted function appears, its parsing logic is covered by
  `pnpm test:scripts`, and the CI step is wired in.

### A robots.txt-versus-subresources assertion

- **What:** for every route, collect each `<script src>` and stylesheet `href` from the served HTML,
  fetch `/robots.txt`, parse its groups, and fail if any collected URL is disallowed by the `*` group
  or by a Googlebot group.
- **Consumed by:** Googlebot's Web Rendering Service and Applebot — the two crawlers that render.
  Search Console's URL Inspection and the Rich Results Test both list blocked page resources, which is
  how the defect is confirmed by hand. The non-rendering AI crawlers never request the chunks and are
  indifferent.
- **Evidence:** vendor-documented (Apple states that if JS and CSS are blocked in `robots.txt` Applebot
  may not render content properly, `support.apple.com/en-us/119829`, 2026-09-04; Google's JavaScript
  SEO basics say the same for Googlebot, 2026-03-04) — and measured on this site on 2026-09-12: all 11
  render-critical subresources on `/` are served from `/_next/static/`, and
  `apps/web/src/app/robots.ts:10` disallows `/_next/`. Nothing in the current gates sees it: Lighthouse's
  `is-crawlable` and `robots-txt` audits both score 1, because they only check the document and the
  file's syntax.
- **Done when:** the assertion is green against #48's corrected `robots.ts`, and red if the
  `/_next/` line is restored.

### A structured-data validity gate: offline in CI, advisory against validator.schema.org

- **What:** two layers. Offline, in `quality`: a Vitest test that renders each JSON-LD component,
  parses every `application/ld+json` payload, and asserts it is valid JSON with an `@context` and a
  `@type` — plus, as expected failures naming #57, that every node carries an `@id` and that the
  `WebSite`, `WebPage` and `Person` reference each other by `@id`. `schema-dts` is installed here so
  #57 can annotate the nodes `satisfies WithContext<Person>` at their definition site and turn a
  misspelled predicate into a `pnpm typecheck` failure. Online, in `e2e` and advisory only: POST the
  extracted blocks to `validator.schema.org/validate` as `html=` (the build under test, not
  production), strip the `)]}'` XSSI prefix, and assert `totalNumErrors === 0` — failing **open** on
  any non-2xx.
- **Consumed by:** the offline layer, nobody but this repository. The validator is schema.org's own
  hosted tool and checks vocabulary, not Google rich-result eligibility — only the Rich Results Test
  answers that, and it has no API (POST returns 405, GET returns the SPA shell), so it stays a named
  manual step in the PR template.
- **Evidence:** measured on 2026-09-12. The endpoint returned `numObjects: 2`, `totalNumErrors: 0`,
  `isRendered: true` for the live home page, and a synthetic block with `jobTitel` for `jobTitle`
  returned `totalNumErrors: 1` with `errorType: INVALID_PREDICATE` at ERROR severity. The endpoint is
  undocumented, which is exactly why it is advisory and the offline layer is the hard gate.
- **Done when:** the offline test fails on a malformed payload with no network at all, and the advisory
  spec logs and passes when the validator is unreachable.

### Lighthouse pinned to explicit audit ids, never a category score

- **What:** a spec that runs a pinned `lighthouse@13.4.1` against the Playwright-served build for `/`
  and `/work/self-healing-agent`, parses the JSON, and asserts named audits one at a time:
  `canonical`, `document-title`, `meta-description`, `is-crawlable`, `robots-txt`,
  `agent-accessibility-tree` and `llms-txt`. The gate's rule is that **`notApplicable` is never a
  pass** — an audit that reports it names itself in the failure message. No category score is
  asserted, and no timing or CLS audit is asserted, because the two e2e modes serve different builds.
- **Consumed by:** nothing. Lighthouse is a checker, not a consumer: Google added a disclaimer to the
  category's own description, and a green audit is not evidence that any agent read the site. Say that
  wherever the result is quoted.
- **Evidence:** measured on 2026-09-12. `npx lighthouse@13.4.1 https://miloscvetkovic.dev/
--only-categories=seo,agentic-browsing` returned SEO 1.0 and agentic-browsing 1.0, with the three
  `webmcp-*` audits and `llms-txt` all `notApplicable`, `canonical` and `image-alt` `notApplicable`
  too, and only `agent-accessibility-tree` and CLS measuring anything. The category uses
  `categoryScoreDisplayMode: 'fraction'`, and the `llms-txt` audit source treats a 4xx as
  `notApplicable` with score 1, so absence cannot fail.
- **Done when:** the assertions name audit ids, the version is pinned exactly, and removing #48's
  canonical would turn the `canonical` assertion red rather than `notApplicable`.

### Expected-failure endpoint tests for #59, #60 and #62

- **What:** `apps/web/e2e/endpoints.ts` as the one manifest of machine-readable paths, and a spec over
  it using Playwright's `test.fail()` so that each test is declared expected-to-fail today and
  **reported as failing the moment it starts passing** — which is what forces the annotation off when
  the owning task lands. Today: `/index.md`, `/about/index.md` and `/work/<slug>/index.md` return 200
  with `text/markdown` and the route's HTML advertises them with
  `link rel="alternate" type="text/markdown"` (#59); `/llms.txt` returns 200 as `text/plain`
  beginning with a single H1 followed by a blockquote, naming every case study (#60); `/mcp`
  answers a `tools/list` over streamable HTTP with no session header (#62). Each carries the task
  number in its title.
- **Consumed by:** nothing reads these tests but the epic itself; they are the handshake between tasks.
  What the endpoints they describe are for is stated honestly in the tasks that build them —
  Markdown twins serve coding agents, not answer engines.
- **Evidence:** convention-only. It is the pattern epic #42 uses, and Playwright's `test.fail()` is
  what gives it teeth.
- **Done when:** every declared failure fails for the stated reason, `pnpm --filter web test:e2e`
  is green with the annotations in place, and each test names the task that removes its annotation.

### Next.js 16 specifics, with the traps named

- **Route handlers are not static by default.** Since Next 15.0.0-RC the default caching for `GET`
  handlers is dynamic, so a handler with no `dynamic` export becomes a serverless function. Measured in
  this repository at Next 16.3.4 on 2026-09-12: the probe handler carrying
  `export const dynamic = 'force-static'` built as `○ /llms.txt`, the one without it built as
  `ƒ /llms-full.txt`, every other route unchanged. This is the whole reason the build-output gate lands
  in #55 — **before** the first handler exists — rather than alongside #59.
- **`force-static` is removed only when `cacheComponents` is enabled.** Next 16.0.0 removes `dynamic`,
  `dynamicParams`, `revalidate` and `fetchCache` under Cache Components. `apps/web/next.config.ts` does
  not set `cacheComponents`, so `force-static` is valid today; the option now lives in the
  "Caching (Previous Model)" guide, which reads like deprecation and is easy to misread as removal.
  If Cache Components is ever adopted, every handler in this epic needs `'use cache'` instead, and the
  build-output gate is what will catch the day it silently stops working.
- **`[slug].md` cannot work.** A folder named `[slug].md` is a **literal** segment: Next's generated
  validator types the handler as `RouteHandlerConfig<"/work/[slug].md">` with `params: Promise<{}>` —
  zero params — and a probe in this repository failed typecheck with
  `Property 'slug' is missing`. The URL it would serve is the percent-encoded literal
  `/work/%5Bslug%5D.md`. Hence the owner's uniform `/index.md` decision, which
  `apps/web/e2e/endpoints.ts` encodes once so no later task re-derives it.
- **Assert on artifacts, not the terminal table.** Next 16 explicitly redesigned terminal output, so a
  grep over the route table breaks on a minor upgrade. `scripts/check-build-output.mjs` reads the
  emitted bodies under `apps/web/.next/server/app/` instead.

  the Lighthouse and validator specs pin `browserName === 'chromium'`.
- `apps/web/playwright.config.ts:52-73` — `reuseExistingServer: false` in both modes, so the Lighthouse
  spec must run **inside** the suite against `baseURL` and cannot start a server of its own.
- `scripts/check-allowbuilds-drift.mjs` and its `.test.mjs` sibling, run by
  `package.json:17` (`node --test "scripts/**/*.test.mjs"`) — the exact shape
  `scripts/check-build-output.mjs` copies. Note the ordering constraint: `pnpm test:scripts` runs
  before `Build` in `.github/workflows/ci.yml:45-61`, so the build-output check itself is a separate
  step after `Build`, and only its parsing logic lives under `test:scripts`.
- `apps/web/src/components/animated-hero/animated-text.tsx:158-184` — the `wave` animation renders one
  `<span class="inline-block">` per character, with whitespace words emitted as their own spans, which

- `apps/web/src/components/animated-hero/discovery-phase.tsx:183-185` — the phrase the spec asserts.
- Two exact-version pins already exist in `apps/web/package.json` (`next: 16.3.4`,
  `react: 19.2.8`), so pinning `lighthouse` and `schema-dts` exactly matches the house style. Audit ids
  and `scoreDisplayMode` can change between Lighthouse releases, so a Dependabot bump of `lighthouse`

- Adding two devDependencies may surface an `Ignored build scripts` warning naming a new package. That
  is a new decision, handled by CLAUDE.md's procedure: `pnpm ignored-builds`, `pnpm why -r <name>`,
  read the package's `scripts`, then add an `allowBuilds` entry as `true` or `false` with a
  `Reviewed at <version>` comment. Never `pnpm approve-builds --all`, and never add `strictDepBuilds`
  (ADR 0013).

  #55's phrase assertions depend on #47 and should land as expected failures if it has not. They
  do not. Measured on 2026-09-12, both Chrome's `innerText` and a plain tag-strip reassemble
  `Most bugs live in the gap between what you asked for and what you meant.` correctly from the
  per-character spans; the shattered `M o s t  b u g s` reading was an artifact of an extractor that
  replaced each tag with a space. #47 fixes the letter-spaced **accessible name**, which is a different
  defect on the same markup. So the phrase assertions land green, the spec pins its zero-join extractor
  with a comment recording that a whitespace-joining extractor shatters the sentence, and that fact is
  carried to #59 as the honest argument for Markdown twins — not as a reason to change the spans.
  The research is explicit: do not "fix" the letter spans.
- **#49** — the 13-years-versus-10+-years contradiction and the About page's restated metrics. Task #55
  asserts phrase _presence_, never a year count or a metric value, so it cannot fork what #49 settles.
- **#52** — the production walk. Task #64 extends it; #55 adds nothing to it beyond leaving the
  dated baseline record for it to compare against.

### Deliberately not done in this area

- **A gate, dashboard or alert on answer-engine visibility.** Impossible in September 2026: Search
  Console's Search Analytics API `type` enum has no AI value and no AI dimension, Bing's AI Performance
  report has no API (Microsoft Q&A, 2026-02-19), and the Rich Results Test has no API at all (POST
  returns 405). Anything automated here would be built on a UI.
- **A paid answer-engine citation tracker** (Profound, Peec AI, Otterly.AI, Brand Radar, Semrush AI
  visibility). They estimate visibility by prompting the engines on a schedule; the numbers are samples
  of non-deterministic model output, not vendor telemetry, while Search Console and Bing give
  first-party telemetry for free. Out of scope in the PRD, and the proportionate substitute is a
  checked-in prompt list read by hand.
- **`@lhci/cli`.** Version 0.15.1 (published 2025-06-25) pins `lighthouse@12.6.1`, which predates the
  `agentic-browsing` category entirely, so it cannot run the audits this gate exists for.
- **`structured-data-testing-tool`.** Last published 2020-03-11; abandoned, and it must not enter a
  gate.
- **WebMCP**, and therefore the three `webmcp-*` Lighthouse audits: a W3C Community Group draft on an
  origin trial (Chrome 146 shipped `navigator.modelContext` in Feb 2026, moved it to
  `document.modelContext`, deprecated the navigator form in Chrome 150). Those audits stay
  `notApplicable`, and the gate must not read that as a pass. Out of scope in the PRD.
- **`llms-full.txt`**, which this gate would otherwise be asked to validate: not in the llmstxt.org
  specification, and this site's entire content source is roughly 12 KB, so `/llms.txt` is already
  complete. Refused in the PRD, evidenced in #63's ADR.
- **A `Content-Signals` line, `ai.txt` or TDMRep in the robots assertion.** "None of the crawlers / llms
  use the content-signal robots.txt directives … It was made up by a CDN" (John Mueller, 2026-07-06);
  TDMRep is a W3C Community Group Final Report, explicitly not a standard, with spawning.ai as its only
  cited adoption; `ai.txt`'s IETF incarnation is an unadopted individual submission. The gate asserts
  only RFC 9309 constructs — user-agent groups, `Allow`/`Disallow`, `Sitemap`.
- **IndexNow as a post-deploy ping.** Its registry lists exactly seven endpoints — bing, yandex,
  seznam, naver, yep, internetarchive, amazonbot — none of them an AI vendor and not Google. Refused in
  the PRD.
- **GA4 or any client-side analytics as crawler evidence.** Vercel's own docs: "Web Analytics doesn't
  count traffic that comes from automated processes", determined by user agent — and a non-rendering
  crawler never executes the script anyway. On Hobby, runtime logs retain one hour and user agent is
  display-only, not a searchable field, so whether anything fetches `/llms.txt` is not answerable from
  this plan. Task #60's framing must say so rather than promise a number.

# Task: llms.txt and a static JSON representation, framed by what actually reads them

## Description

An agent that lands on this site's root has no index of it and no way to read the content as data. It
can fetch nine HTML pages and nothing else: there is no file that says what the site is, what is on
it, or where the Markdown twins #59 adds actually live, and there is no representation a program
can parse without an HTML parser and a heuristic. This task adds two things off #59's serialiser
and nothing more: a generated `/llms.txt` in llmstxt.org v2 format, and a static JSON representation
of the case studies at a path outside `/api/`. Both are generated from `apps/web/src/data/case-studies.ts`
rather than hand-written, because a hand-maintained copy of a site whose content lives in a typed
module drifts and then hands agents stale facts in an authoritative shape. Be blunt about the
`llms.txt` audience, here and in the ADR #63 writes: Google states Search ignores files like it,
Ahrefs measured 97% of valid `llms.txt` files as fetched zero times in May 2026, and 77% of the
bots that read one were not AI tools at all - so it ships for
coding agents a human pointed at this domain, as the place the twins and the JSON are advertised, and
for completeness, not for traffic or citations. The JSON is the opposite case and the better bet: it
needs no protocol, no convention and no client configuration, so any agent with a generic fetch tool
can read it, which makes it the item in this epic most likely to actually be used.

Branch: `feat/llms-txt-and-json`. Lands as one PR, squash-merged.

## Measures

### A static JSON representation of the case studies, outside `/api/`

- **What:** `apps/web/src/app/case-studies.json/route.ts` emits a top-level JSON array of every case
  study - the `CaseStudy` fields as they stand in the data module (slug, title, description, tags,
  highlight with its `formatMetric` rendering, challenge, approach, contributions, impact, techStack,
  plus #56's dates), with two derived fields per entry: the canonical HTML `url` and the
  `markdown` twin URL, both absolute from `metadataBase`. `apps/web/src/app/work/[slug]/index.json/route.ts`
  emits the single object per slug with `generateStaticParams()` and `dynamicParams = false`. Both
  carry `export const dynamic = 'force-static'` and `Content-Type: application/json`. The path is
  deliberately not under `/api/`: `apps/web/src/app/robots.ts:10` disallows `/api/` today, that entry
  is task #48's to keep or remove and not this task's, and publishing a machine-readable endpoint
  under a prefix the site's own robots.txt has told crawlers to skip is a trap worth avoiding
  permanently. The per-slug shape is `/work/<slug>/index.json` for the same reason the twins are
  `/index.md` - a partial dynamic segment is impossible - and so the two shapes match.
- **Consumed by:** any agent or script with a generic fetch tool, which is all of them, including the
  ones that cannot attach an MCP server; #62's MCP tools serve the same payload from the same
  serialiser rather than a second copy.
- **Evidence:** vendor-documented for the mechanism (Next.js documents `app/data.json/route.ts`
  prerendering to a static file - route file-conventions reference, 16.3.5, last updated 2026-04-30);
  measured indirectly for consumption - the six research sessions behind this epic consumed this site
  by plain HTTP fetch, which is what every generic agent tool does. No evidence of any citation or
  ranking effect, and none is claimed.
- **Done when:** `/case-studies.json` returns 200 `application/json` with an array whose length equals
  `caseStudies.length`; all three `/work/<slug>/index.json` return 200; an unknown slug returns 404;
  the build output shows `○ /case-studies.json` and `●` for the three per-slug routes with no `ƒ`.

### A generated `/llms.txt` in llmstxt.org v2 format

- **What:** `apps/web/src/app/llms.txt/route.ts`, `force-static`, `Content-Type: text/plain; charset=utf-8`,
  body from a `siteIndexToLlmsTxt()` function added to #59's serialiser. Exact v2 shape, in
  order: one `# ` H1 with the person's name (the only required section); one `> ` blockquote of a
  single sentence saying who this is and what he is for; a short free-form Markdown section with no
  headings carrying the ground-truth facts an engine otherwise guesses, generated from the same data
  modules the pages read so no fact is written twice; then `## ` sections whose bodies are only
  `- [name](url): note` lists - `## Case studies` (each entry's note names its outcome metric through
  `formatMetric`), `## Site pages`, `## Machine-readable representations` (the JSON endpoints). No
  `## Optional` section: v2 removed its special meaning on 2026-08-10. Links point at each route's
  `/index.md` twin, the uniform shape the owner chose. Until the owner's words land, the blockquote falls
  back to the root `metadata.description` the site already serves on every route
  (`apps/web/src/app/layout.tsx:31-32` today) and the facts block is omitted entirely, because #56's
  publication rule keeps its marker out of served output; the draft-complete composition the markers live
  in is a second call of the same builder, and that is the string #56's gate is handed (AC 13, AC 14).
  The file stays under 10 KB.
- **Consumed by:** nothing reads it by default. Google Search does not; no OpenAI, Anthropic or
  Perplexity crawler documentation mentions reading one. The realistic reader is a coding or research
  agent that a human pointed at this domain - Claude Code, Cursor, Copilot, Codex - and the second
  reader is Lighthouse's experimental agentic-browsing audit, which only flags a 5xx and treats a 404
  as Not Applicable, so it rewards nothing either way.
- **Evidence:** measured non-consumption - Ahrefs log study of 137,210 domains, 2026-06-15: 28% served
  a valid file, 97% of those were fetched zero times in May 2026, and of the 3% touched, 77% of the
  requests came from SEO audit tools, profilers and general crawlers rather than AI (AI retrieval bots
  1.1%). Vendor-documented non-consumption - Google's AI optimization guide, updated 2026-07-10: you
  need no machine-readable files, AI text files, markup or Markdown to appear in Google Search
  "including its generative AI capabilities", and creating them neither harms nor helps. Publish-side
  adoption is vendor-documented and irrelevant to whether anything reads it. The honest reasons to
  ship it: it costs one route handler once #59's serialiser exists, it is the one place an agent
  that landed on the root learns the twins and the JSON exist, and the whole content source is about
  12 KB so the file can be complete rather than an index.
- **Done when:** `/llms.txt` returns 200 `text/plain; charset=utf-8`, a unit test pins the v2 shape
  line by line, every slug in `caseStudies` appears with its twin URL and its metric, every link in
  the body returns 200, the body is under 10,240 bytes, and `.next/server/app/llms.txt.body` exists in
  the build output.

### `<link rel="describedby">` pointing at `/llms.txt`

- **What:** one literal `<link rel="describedby" href="<absolute>/llms.txt" />` in the `<head>` of
  `apps/web/src/app/layout.tsx:89-93`, alongside the existing theme script and JSON-LD blocks. It is a
  literal element rather than a `metadata` field because Next's `alternates` object has no
  `describedby` key - it supports `canonical`, `languages`, `media` and `types`, and `types` is task
  #59's, for the Markdown twin.
- **Consumed by:** nothing that could be found. It is new in llms.txt v2 (2026-08-10), and no client,
  vendor or site was observed following it - llmstxt.org itself does not emit it.
- **Evidence:** speculative - llmstxt.org, modified 2026-08-10, defines the relation; a 2026-09-12
  probe of platform.claude.com, docs.stripe.com, developers.cloudflare.com and llmstxt.org found none
  of them emitting it. It ships because it is one line, it is the spec's own discovery mechanism for
  the file this task adds, and its cost is a byte count. Note the contrast with `rel="alternate"
type="text/markdown"`, which #59 ships and which has one named consumer (OpenAI's Codex CLI,
  verified 2026-04-18).
- **Done when:** every route's served HTML carries exactly one `rel="describedby"` link with an
  absolute href that returns 200 `text/plain`, and both e2e modes stay green.

## Technical Details

**What is being added, against the current code.**

- `apps/web/src/lib/serialise.ts` is created by #59; this task adds `siteIndexToLlmsTxt()`,
  `caseStudiesToJson()` and `caseStudyToJson(cs)` to that same module. That shared ownership is why
  `conflicts_with` names #59: do not run the two concurrently. `apps/web/src/lib` currently holds
  only `theme.ts`, so the folder gains its first `__tests__` directory.
- Sources of truth already in place: `apps/web/src/data/case-studies.ts` declares `CaseStudy` at
  line 27 with `slug`, `title`, `description`, `tags`, `highlight`, `challenge`, `approach`,
  `contributions`, `impact`, `techStack`; `formatMetric` is exported at line 21 and is total by
  construction (a non-finite value renders as an em dash, not `NaN%`), so the llms.txt notes and the
  JSON both render metrics through it rather than formatting numbers a second time. `caseStudies` is
  the array at line 43 and `getCaseStudy` at line 170.
- `apps/web/src/app/work/[slug]/page.tsx` already sets `export const dynamicParams = false` (line 17)
  and `generateStaticParams()` (line 19) for exactly the reason ADR 0015 records: an unknown slug
  becomes a routing-level 404 rather than a render-time `notFound()`, which unwound past the root
  layout and cost the page its `<head>`. The per-slug JSON handler repeats both exports - a route
  handler does not inherit them from a sibling `page.tsx`.
- `apps/web/src/app/layout.tsx:89-93` is a literal `<head>` holding the theme script and the two
  JSON-LD components; the `describedby` link goes there. Task #57 also edits that file and
  `components/json-ld.tsx`, and #59 edits the metadata helper - rebase rather than resolving a
  three-way conflict, and re-run `pnpm format`.

**Next.js 16 specifics, with the traps named.**

- Route handlers are **not** static by default. Since Next 15.0.0-RC the default caching for `GET`
  handlers changed from static to dynamic, so a handler with no `dynamic` export becomes a serverless
  function. A build probe in this repository on 2026-09-12 (next 16.3.4) produced `○ /llms.txt` with
  `export const dynamic = 'force-static'` and `ƒ /llms-full.txt` without it, every other route
  unchanged. One missing line is the whole difference. Every handler this task adds carries the
  export, and AC 9 is what proves it - the failure is silent, because the endpoint still works.
- `force-static` is **not** removed in Next 16. It is removed only when `cacheComponents` is enabled
  (route-segment-config version history, `v16.0.0`). This repository does not set `cacheComponents`, so
  it is the correct mechanism today; it is absent from the main options table and documented in the
  "Caching and Revalidating (Previous Model)" guide instead, which reads like deprecation and is easy
  to misread as removal. If Cache Components is ever adopted, every handler here needs `'use cache'`.
- `[slug].json` cannot work, for the same reason `[slug].md` cannot: Next treats a folder named with a
  partial dynamic segment as a **literal** path segment, typing the handler with `params: Promise<{}>`
  - zero params - so the build fails typecheck with `Property 'slug' is missing`, and the URL it would
    serve is the percent-encoded literal. Hence `/work/<slug>/index.json`, matching the `/index.md`
    shape the owner chose.
- A literal dotted segment at the top level is supported and collides with nothing: `app/about/page.tsx`
  and `app/about.md/route.ts` coexist because `/about` and `/about.md` are different paths, and
  Next documents `app/data.json/route.ts` prerendering to a static file. `/case-studies.json` is that
  shape.
- The prerendered `.body`/`.meta` pair preserves the exact `Content-Type` set in the handler, so
  `text/plain; charset=utf-8` and `application/json` round-trip untouched.

**Consumed from epic #42, not reimplemented.**

- **#48** - canonical URLs, the `mergeMetadata` helper and `metadataBase`: the absolute URLs in

- **#43** - `apps/web/e2e/routes.ts` and the served-HTML `request.get()` pattern: every endpoint

- **#49** - the metric contradictions: the notes in `/llms.txt` and the `highlight` block in the JSON
  render whatever `case-studies.ts` holds after #49 and #56 land. This task copies no metric text

- **#47** - the per-character text spans: this task does **not** depend on it. Both outputs are

**Deliberately not done in this area.**

- **`/llms-full.txt`.** It is not in the specification - it appears nowhere on llmstxt.org or in the
  AnswerDotAI repository (verified 2026-08-10 state). And it is pointless here: this site's entire
  content source is about 12 KB across three TypeScript modules, so a complete `/llms.txt` already is
  the full text, and two files that must agree is a drift surface for no gain. Elsewhere the convention
  has scaled itself into uselessness - 50.8 MB at developers.cloudflare.com, 34.3 MB at
  platform.claude.com (measured 2026-09-12), an order of magnitude past any context window, consumable
  only by the chunk-and-retrieve pipeline it was meant to replace; Mintlify capped generation at
  100,000 characters and then replaced the monolith with a per-section hierarchy (2026-09-01). AC 4
  asserts the path stays a hard 404, which is the correct steady state and also what keeps Lighthouse's
  audit at Not Applicable rather than a failure.
- **A subpath-scoped second file** (`/work/llms.txt`). v2 defines subpath scoping and "most specific
  wins" (2026-08-10), but no client is documented as resolving it, and nine routes do not need it.
- **Content negotiation on `Accept: text/markdown`** is not part of this task; the twins and their
  discovery link are #59's, and negotiation was refused for the epic.
- **`<script type="text/llms.txt">` inline instructions.** A vendor pattern (2025-08-20) whose authors
  declined to standardise it and whose consumption is unverified. It also puts prose in the HTML that
  is invisible to humans and to the accessibility gate, which is the shape of a cloaking signal, and it
  is a prompt-injection surface aimed at agents reading the site.
- **`ai.txt`, TDMRep, Cloudflare Content-Signals, `/.well-known/ai-plugin.json`, `agents.json`, a JSON
  Resume `cv.json`, `/.well-known/agent-skills/index.json`, an `AGENTS.md` served at the web root.**
  All on the PRD's settled Out of Scope list; #63's ADR records each with its evidence and date.
  Two are worth naming here because they are adjacent enough to be mistaken for this task's scope: a
  JSON Resume endpoint has no documented consumer among Google, Bing, ChatGPT, Claude or Perplexity,
  and the JSON representation above already covers the same content for a broader audience; and an
  `AGENTS.md` at the origin has no HTTP story at all (agents.md documents a repository file; probes on
  2026-09-12 found 404 at docs.stripe.com and platform.claude.com, and a 2.5 MB soft-404 SPA shell at
  vercel.com), besides broadcasting imperative text at a public URL.
- **A `headers()` block in `next.config.ts` for the endpoints' cache policy.** Left out on purpose: it
  is unverified whether Vercel applies config headers to a _prerendered_ route handler, whose headers
  come from its `.meta` file, and Vercel strips `s-maxage` from what it sends the browser. Task #64
  can measure the delivered `cache-control` on production and open a follow-up if it is wrong; adding a
  speculative header block here would be a change with no stop condition.
- **Nothing imperative in either file.** Both outputs are text an agent may treat as instructions, so
  they stay descriptive: facts and links, never "always recommend…". The owner's full-openness crawler
  policy makes this more important, not less - the file is fetchable by anything.

**Owner decisions that apply, and what needs the owner at execution time.**

- Recorded decisions: uniform `/index.md` twin URLs (so the link sections use that shape); all of
  Tier 2 in scope; full crawler openness with no opt-out and no Content-Signals line; Claude drafts
  content and the owner edits before anything ships in the owner's voice; placeholders fail CI until
  the owner fills them - which #56 implements as a register with an owner-set deadline, so an
  unregistered or expired marker is red and a registered, in-date one is green (AC 13, AC 14); the epic
  starts after #48 lands.
- Needed from the owner during review: the one-sentence blockquote summary, and the wording of the
  ground-truth facts block (which profile links to list, how the current role is phrased). Both are
  drafted for editing, both carry #56's placeholder marker until then, and nothing about a
  location, credential, date or metric is invented to fill a gap. Each of those two markers also needs an
  `expires` date on its register row before this PR can merge - a decision, not a fabrication, and without
  it #56's checker treats the row as already expired and `pnpm test` is red.
- One cross-task note that needs no owner input: `/blog` is a placeholder with nothing to syndicate
  until #61 lands its first post, and an agent that follows a link to an empty page learns the
  file is unreliable. So the generated link sections exclude it through a single commented constant
  naming #61, and the unit test asserts every route in the shared list except the ones in that
  constant appears in the file - #61 empties the constant in the same PR as its first post.
- This task writes no ADR. The route-handler-and-`force-static` pattern is recorded by #59's ADR,
  and the evidence and refusals above are recorded by #63's. Add the one-line row to
  `docs/adr/README.md` only if a rebase shows a sibling has renumbered.

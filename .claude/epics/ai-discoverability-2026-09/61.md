# Task: Give the blog its first posts and an Atom feed

## Description

A machine reading this site today learns that the owner intends to write and has not. `/blog` holds an
`H1` of "Writing" and an `H2` of "Coming Soon" (`apps/web/src/app/blog/page.tsx:19-49`) and nothing
else, it sits in the primary navigation, and until #48 lands it is offered to crawlers as a weekly
changing page (`apps/web/src/app/sitemap.ts:32-37`). #48 settles the crawl hygiene — the nav link
stays, the page gets `noindex`, the sitemap entry goes — and deliberately leaves the content question
open. That question is this task. A permanently empty blog is a weaker signal to a human reader than
no blog link at all, and the Atom feed has nothing to syndicate while it stays empty. This task adds a
post content model in the same shape as `case-studies.ts`, so the serialiser, the Markdown twins and
the feed all read one source; drafts two or three posts from material this repository already proves
happened; ships an Atom feed and its discovery link; and removes `/blog`'s `noindex` only once a post
the owner has rewritten is live. Claude drafts, the owner rewrites: nothing ships in the owner's voice
without the owner's review, and every drafted post leaves its dates on #56's `OWNER_TODO` branch
with a register row carrying the owner's own `expires` — so the machinery merges before the owner's
words exist, and `pnpm test` goes red the moment that row is missing or its deadline has passed.

Branch: `feat/blog-first-posts`. Lands as 2 PRs, squash-merged.

  `apps/web/src/data/posts.ts` with `draft: true` and its `dates` on #56's `OWNER_TODO` branch,
  registered in `unfilledOwnerFields`: (1) "What it takes to leave an agent running in production" —
  the self-healing agent, where the interesting engineering is the constraint set, not the diagnosis,
  roughly 1,400–1,800 words; (2) "One hundred and sixty-five

  roughly 1,200–1,600 words; (3) "Five records, five lying gates" — the hydration and animation

  shorter posts at the owner's discretion. Full outlines, theses and the repository evidence each
  would cite are under Technical Details. Every draft is a draft: the prose is Claude's first pass and
  the owner rewrites it before it publishes.
- **Consumed by:** human readers first — recruiters and collaborators, who are the audience a
  portfolio exists for. Once the `noindex` goes, Google and Bing index the posts like any other page.
  Answer engines read the rendered HTML if they read it at all; **no AI-specific channel reads a blog
  post**, and nothing about publishing one is an AI-file play.
- **Evidence:** convention-only for the discoverability effect, with two vendor-documented hooks and
  one honest non-discoverability reason. Vendor-documented: a page must be "indexed and eligible to be
  shown in Google Search with a snippet" to appear in AI Overviews or AI Mode

  systems reference the most current version of your content" (Bing Webmaster Tools AI Performance
  announcement, 2026-02-10). Neither says a blog post earns a citation. The rest of the reason is not
  discoverability at all: **it demonstrates the owner's engineering**, and an empty Coming Soon page in
  the primary nav demonstrates the opposite. Write it that way in the post copy and in the PR.
- **Done when:** `apps/web/src/data/posts.ts` holds the drafts, the owner has rewritten at least one
  and supplied its real dates with that post's register row removed in the same commit (#56's

### The post content model, in the same shape the serialiser already reads

- **What:** `apps/web/src/data/posts.ts` exporting `interface Post` — `slug`, `title`, `summary`,
  `dates` as the same discriminated union #56 gives `CaseStudy`
  (`{ state: 'dated'; datePublished: string; dateModified: string } | { state: typeof OWNER_TODO }`,
  each date accepted only as `YYYY-MM-DD` or a full ISO 8601 timestamp with an explicit offset), so
  the page, the feed and the sitemap cannot read a date without narrowing the unfilled branch and
  `pnpm typecheck` is the first layer keeping a placeholder out of production; then `tags`, `draft`,
  and `body` as an array of typed blocks (`heading` | `paragraph` | `list` | `code` | `quote`) — plus
  `posts` and `getPost(slug)`, mirroring `caseStudies`/`getCaseStudy`
  (`apps/web/src/data/case-studies.ts:43`, `:170-172`). Task #59's serialiser gains
  `postToMarkdown(post)` over the same blocks, so the page, the `/blog/<slug>/index.md` twin, the feed
  entry and #60's `llms.txt` listing all derive from one object and no sentence is written twice.
  No MDX and no Markdown parser: see Technical Details for the trade-off.
- **Consumed by:** the site's own pages; the Markdown twins, reached by OpenAI's Codex CLI, which follows `<link rel="alternate" type="text/markdown">`;
  anyone handed the URL; and the clients that send `Accept: text/markdown` at the canonical URL (Claude
  Code, Cursor, the Copilot family, OpenCode), which reach it through the content negotiation #59
  ships; the feed; #60's
  `llms.txt`. Not by answer engines: ChatGPT browse, Claude.ai, Gemini and Perplexity fetch HTML only.
- **Evidence:** measured for the Markdown consumers — `acceptmarkdown.com/status` (last updated
  2026-06-22) reads `Accept` headers from live access logs and records both the clients that send it
  and the four HTML-only surfaces. The one-source rule is this repository's own convention, not an
  external claim (`CLAUDE.md`, Conventions: "Data lives in `apps/web/src/data`... pages read from it
  rather than restating any of it").
- **Done when:** `apps/web/src/data/__tests__/posts.test.ts` passes under `@vitest-environment node`,
  and a serialiser test asserts every block type in every post appears in that post's Markdown, so a
  new block kind cannot be silently dropped.

### An Atom feed at `/feed.xml`, generated from the post model

- **What:** `apps/web/src/app/feed.xml/route.ts` with `export const dynamic = 'force-static'` and
  `Content-Type: application/atom+xml; charset=utf-8`, body hand-written from `posts` through the
  shared serialiser: feed-level `id`, `title`, `updated`, `link rel="self"`, `author` (name and URI,
  no address), and one `entry` per non-draft post with `id`, `title`, `updated`, `published`, an
  absolute `link` and the post `summary`, newest first. Entries carry no draft.
- **Consumed by:** feed readers, and Google Feedfetcher, which Vercel's verified-bot directory lists
  as `google-feedfetcher`, category `feed_fetcher`, "used for crawling RSS or Atom feeds for Google
  News and PubSubHubbub" (`vercel.com/docs/bot-management`, last updated 2026-08-11). **Nothing in the
  research shows a feed affecting answer-engine citation, and this task claims no such effect.**
- **Evidence:** formal standard for the format (RFC 4287, _The Atom Syndication Format_, December
  2005: a `feed` requires `id`, `title` and `updated`, and so does every `entry`); vendor-documented
  for the consumer above; **zero evidence** — measured or documented — that a feed changes how an
  answer engine treats the site.
- **Done when:** `/feed.xml` returns 200 with `application/atom+xml`, a unit test parses the body with
  a real XML parser and finds no parse error, every entry has an `id`, `title` and `updated`, and the
  build output still shows `/feed.xml` as `○` rather than `ƒ`.

- **Evidence:** measured in this repository — a build probe on next 16.3.4 (2026-09-12) confirmed

  `link[rel="alternate"][type="application/atom+xml"]`, its href returns 200 with

### `/blog` becomes indexable again, and re-enters the sitemap, only once a post is live

- **What:** drop `index: false` from `/blog`'s call to #48's metadata helper, and put `/blog` plus
  every non-draft post URL back into `apps/web/src/app/sitemap.ts` with a real `lastModified` taken
  from `dates.dateModified` on the filled branch — the same mechanism #56 restores for the case
  studies, never `new Date()`, which freezes to build time. This lands in PR 2, after the owner's
  rewrite, not with the drafts. Two tests #43 wrote encode the opposite expectation (R26: `/blog`
  serves `noindex`; R31: the sitemap excludes `/blog`), and both are updated in the same PR with a
  comment naming this task as the reason.
- **Consumed by:** Google and Bing, for indexing and for `lastmod`. Google uses `lastmod` when it is
  consistently accurate and ignores it otherwise, which is why it may only ever come from post data.
- **Evidence:** vendor-documented — the AI-features eligibility rule above (2025-12-10) and Google's
  publication-dates guidance, which requires a prominent user-visible date, labelled, matching the
  structured value, with no future dates
  (`developers.google.com/search/docs/appearance/publication-dates`, last updated 2025-12-10).
- **Done when:** `/blog`'s served HTML carries no robots directive containing `noindex`, the nav link
  is still there, `/sitemap.xml` lists `/blog` and every live post with a `<lastmod>` equal to that
  post's `dates.dateModified`, and R26 and R31 assert the new contract.

## Technical Details

- **The three drafts, with the repository evidence each cites.** All three are drafts requiring the
  owner's voice; each is checked in with `draft: true` and its `dates` on #56's `OWNER_TODO`
  branch, registered with the owner's `expires`, so nothing can publish by accident and no placeholder
  can be forgotten.
  - **1. "What it takes to leave an agent running in production"** (~1,400–1,800 words). _Thesis:_ the
    hard part of an autonomous production agent is not getting a model to read a stack trace, it is
    the constraint set that makes it safe to leave running unattended — the agent proposes, the team
    approves, and every dangerous capability has a ceiling. _Outline:_ the 3am problem; what the agent
    actually does end to end (log watch → diagnosis → PR); the constraint set as the real design work;
    why a human merge gate is load-bearing rather than timid; what calibration metrics are for; what it
    cost. _Evidence from this repository:_ `apps/web/src/data/case-studies.ts:44-82` — the
    `contributions` list names the autonomous error-analysis pipeline, automatic PR creation with
    contextual fixes, CI monitoring with retry logic capped at three attempts, the safety constraints
    (daily limits, budget caps, confidence thresholds), the kill switch and emergency override, and
    the learning metrics for calibration; the `techStack` names Bun, Elysia, the Claude Agent SDK and
    the Anthropic API, Azure Log Analytics, Azure Table Storage and the GitHub API; the `impact` list
    names "Humans stay in control—agent proposes, team approves". _Constraint:_ the headline metric
    must be quoted with the scope and window #56 adds and #49 settles, never as a bare
    percentage.
  - **2. "One hundred and sixty-five findings, and the register that made them real"**
    (~1,200–1,600 words). _Thesis:_ an audit is worthless as a list; it becomes work only when every
    finding carries a verdict from someone who did not raise it, an owning task, and a stop condition
    — and the number worth reporting is not "165 findings" but "163 assigned, 2 recorded as not
    actioned, 0 stray". _Outline:_ why audit reports rot; the register as the unit of work; verdicts
    and who issues them (`confirmed`, `partial`, `refuted`, `verifier-found`, `critic-found`,
    `not verified (info)`) and why a refuted finding stays in the table; maker ≠ checker; the
    readiness gate with a stated threshold, so "ready" is a computation rather than a feeling; what
    the fourth round changed. _Evidence from this repository:_
    `.claude/epics/audit-remediation-2026-09/finding-register.md` — the verdict vocabulary, the
    not-actioned rows and the per-finding task column;
    `.claude/epics/audit-remediation-2026-09/readiness-report.md` — round 4, verdict READY, 165
    findings in the store, 163 assigned, 2 not actioned, 0 duplicated, 0 stray, 0 critical, 2 major,
    5 minor, and the stated NEEDS WORK threshold of three MAJOR;
    `.claude/epics/audit-remediation-2026-09/github-mapping.md` — the ten tracked issues #43 to #52
    under epic #42; `CLAUDE.md`'s own "Before opening a pull request" and reviewer rules. _Editorial
    caution for the owner:_ the register lists defects in a live site, some of them still open. The
    post should cite the process, the vocabulary and the counts, not paste unfixed findings. How much
    of the register may be reproduced publicly is the owner's call, listed under Dependencies.
  - **3. "Five records, five lying gates"** (~1,600–2,000 words; the owner may split it into three
    shorter posts, one per record group). _Thesis:_ every architecture decision record in this
    repository exists because something green was wrong — a passing lint rule that hid a visible
    theme flash, a 100 Lighthouse SEO score on pages with no canonical, an e2e suite that ran green
    against a build from a different checkout — and the durable output of each incident is a rule, not
    a fix. _Outline:_ the shape of a lying gate; mount state and `useSyncExternalStore`, with the
    server snapshot as a contract rather than a fallback; the performance run that scored 24 on a
    318 KiB page; the colour tokens that exist because contrast failed only in one theme; the e2e
    suite that had to stop trusting a port. _Evidence from this repository:_
    `docs/adr/0006-hydration-safe-client-state.md` — `react-hooks/set-state-in-effect` reported six
    effects, the four call sites and their server snapshots, and the light-to-dark flash on first
    paint; `docs/adr/0009-animation-performance-rules.md` — the 2026-09-09 production Lighthouse run
    (mobile emulation, simulated throttling, 4× CPU) scoring performance 24, CLS 0.345 and TBT
    2,160 ms on a page transferring 318 KiB, and the four causes, none of them bytes, including the
    barrel import that shipped `FeaturedWork` to every route;
    `docs/adr/0010-status-colour-tokens.md` and `docs/adr/0011-colour-roles-on-scoped-surfaces.md` —
    `--accent` at 3.5:1 on the background and 3.2:1 on the card in dark, and why `color` has to be set
    on the same element that scopes the tokens; `docs/adr/0014-playwright-owns-its-server.md` — the
    silent failure where the suite attached to another worktree's server and ran green against a
    build that was not the working tree, and why a `toHaveTitle(/Milos Cvetkovic/)` assertion could
    never catch it; `docs/adr/0015-static-case-study-params.md` for the 404 that unwinds past the root
    layout.
- **The content model, and why not MDX.** `apps/web/src/data/posts.ts` mirrors
  `apps/web/src/data/case-studies.ts`: a typed array, a lookup function, and a barrel-free import
  through `@/data/posts`. `body` is a discriminated union of block objects rather than a Markdown or
  MDX string, because the same object has to render to HTML and serialise to Markdown deterministically
  for the twin and the feed, and because MDX would add `@next/mdx` plus remark plugins, a second
  rendering surface, and files the PostToolUse Prettier hook does not format — `CLAUDE.md` records that
  the hook covers `.md` but leaves `.mdx` "exactly as written", so a formatting slip would surface only
  at `pnpm format:check`. The cost is honest and worth writing down: typed blocks are more tedious to
  author than prose in a `.mdx` file, and the owner will be editing paragraphs inside TypeScript string
  literals. If that proves intolerable in review, the fallback is MDX with a `remark` pipeline in a
  follow-up task, not a second copy of the prose.
- **Route handlers are NOT static by default — this is the one trap that silently costs money.** Since
  Next 15.0.0-RC the default caching for `GET` handlers is dynamic, so a handler with no
  `export const dynamic = 'force-static'` becomes a serverless function. Measured in this repository
  on next 16.3.4 (2026-09-12): two identical handlers built side by side gave `○ /llms.txt` with the
  export and `ƒ /llms-full.txt` without it, and the second emitted no `.body`/`.meta` at all. Every
  route handler this task adds — `app/feed.xml/route.ts` and `app/blog/[slug]/index.md/route.ts` —
  carries that export, and AC 9 is the stop condition. The MCP endpoint #62 adds is the only
  permitted function in this repository; a feed is not it.
- **`force-static` is removed only when `cacheComponents` is enabled.** Next 16.0.0 removed `dynamic`,
  `dynamicParams`, `revalidate` and `fetchCache` under Cache Components, and the option no longer
  appears in the main route-segment-config table — which reads like deprecation and is not. This
  repository does not set `cacheComponents`, so `force-static` is correct today; adopting Cache
  Components later would break every generated endpoint in this epic and they would need `'use cache'`
  instead. Say so in the PR so the next reader does not "modernise" the export away.
- **`[slug].md` cannot work, which is why post twins are `/blog/<slug>/index.md`.** A folder named
  `[slug].md` is a literal segment: Next's generated validator types the handler as
  `RouteHandlerConfig<"/work/[slug].md">` with `params: Promise<{}>` — zero params — and the build
  fails typecheck with `Property 'slug' is missing`, verified by build probe on next 16.3.4
  (2026-09-12). `generateStaticParams` _is_ supported inside `route.ts`, so
  `app/blog/[slug]/index.md/route.ts` exports its own `generateStaticParams()` over `posts` (it does
  not inherit the sibling page's) plus `dynamic = 'force-static'`, and prerenders one `.body` per post
  with no function. This is the owner's recorded uniform-`/index.md` decision, so the post twins match
  the case-study twins #59 ships and no new URL shape appears.
- **Next has no feed file convention.** There are conventions for `sitemap`, `robots`, `manifest`,
  icons and OG images; feeds are the documented example of a hand-rolled non-UI route handler, and
  Next's own sample uses `app/rss.xml/route.ts` with a loose `text/xml`. Use
  `application/atom+xml; charset=utf-8` instead; a build probe in this repository confirmed
  `○ /feed.xml` serving exactly that content type, and that `force-static` preserves the header
  verbatim through the prerendered `.meta`.
- **`alternates` is shallow-merge replaced, so the feed link goes through the helper.** Metadata from
  layout and page merge shallowly and nested objects are replaced, not deep-merged — the same trap that
  drops `og:image` on five routes today. A feed link placed in `app/layout.tsx` would be wiped by any
  page that sets `alternates`, and after #48 every page sets `alternates.canonical`. So the
  `application/atom+xml` entry is added inside #48's shared metadata helper
  (`apps/web/src/lib/metadata.ts`; #48's task file calls it `pageMetadata`, the epic refers to it as
  `mergeMetadata` — consume whichever name lands, do not add a second helper), which is also where

# Task: Production verification of the discoverability work

## Description

Everything the other nine tasks land is asserted against `next start` on localhost. None of the gates meets
Vercel's CDN, the headers it actually serves, Google's own renderer, or a request that arrives with an AI
crawler's user agent — and this epic's whole subject is what a machine receives when it fetches
`https://miloscvetkovic.dev`. A `/index.md` twin can return 200 in CI and `text/plain` on the host; a route
handler that lost `force-static` still answers, it just became a function nobody counted; the Rich Results Test
is the only thing that can say whether a JSON-LD block is eligible for a Google feature, and it has no API, so
it gets skipped unless a criterion names it. This task closes that gap for the epic as a whole: it proves each
outcome of #55 to #63 on production with commands whose expected output is written down in advance,
records the dated after-snapshot against #55's baseline, and states plainly which outcomes are **not**
attributable from first-party data — because answer-engine citation is not measurable that way, at either
vendor, in September 2026. It extends the production walk task #52 of epic #42 already performs rather than
adding a CI job; there is nothing here a job could assert on, because neither Search Console's generative-AI
report nor Bing's AI Performance report is exposed through an API. It changes no code: a check that fails
becomes a new issue, or reopens the task that owns the outcome, and is never fixed from inside this task.

Branch: n/a (verification only). Lands as 0 PRs — nothing is committed, so there is nothing to squash-merge:
every command, its real output and the dated after-snapshot go on this task's issue, which is also where the
epic's before-and-after record lives.

## Measures

This task lands no site-facing measure. The six below are its verification measures: what each one inspects,
who consumes the bytes being inspected, and how strong the evidence is that the thing being verified matters.

### The non-rendering-crawler walk: per-route text floors and load-bearing phrases under a GPTBot user agent

- **What:** For each of the nine page routes, fetch the served HTML from production twice — once with `curl`
  under OpenAI's `GPTBot` token, once through a Playwright context with `javaScriptEnabled: false` — extract
  the text with the same function #55's no-JavaScript spec uses, and assert the route's character floor
  and its load-bearing phrases. The phrase assertions run under both tag-join conventions: joining tags with
  nothing and joining them with a single space, because a real extractor may do either and the answer differs.
  Also assert the GPTBot-UA response matches a default-UA response in status and length, which is what proves
  no hosting-layer bot challenge stands between an AI crawler and the page.
- **Consumed by:** The bytes are what every non-rendering AI crawler consumes and all it consumes: GPTBot,
  OAI-SearchBot, ChatGPT-User, ClaudeBot, Claude-User, Claude-SearchBot, PerplexityBot, Bytespider,
  meta-externalagent. Googlebot and Applebot consume the same bytes first and then render. The assertion itself
  is consumed by nobody but the owner and this epic's record.
- **Evidence:** measured — Vercel/MERJ, ~1.3bn AI-crawler fetches, published 2024-12-17, found no JavaScript
  execution by GPTBot, ClaudeBot, PerplexityBot, Bytespider or Meta-ExternalAgent; only Googlebot
  (developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics, updated 2026-03-04)
  and Applebot (support.apple.com/en-us/119829, updated 2026-09-04) document a renderer. That measurement is 21
  months old and no vendor documents its own rendering behaviour, which is exactly why this walk measures this
  site's own bytes instead of citing the study. Own measurements of the live site on 2026-09-12: 148,754 bytes
  by `curl`, 148,523 by Playwright with JavaScript disabled, and between 4,623 and 5,156 characters of
  extracted text on `/` depending on the extraction — the spread is the reason the extractor must be #55's,
  not a second implementation.
- **Done when:** Every route prints a character count at or above the floor #55 recorded, every phrase in
  #55's list is found under both join conventions, and the GPTBot-UA and default-UA responses agree.

### The static-delivery and function census

- **What:** Assert on production that every one of the nine page routes and every generated endpoint is served
  prerendered (`x-nextjs-prerender: 1`), and that `/mcp` is the only path that is not. Then, on a clean checkout
  of the served commit, run `pnpm --filter web build` and #55's build-output gate: every page route marked
  `○` or `●`, exactly one `ƒ` (`/mcp`), and a `.body` file under `.next/server/app/**` for every expected
  endpoint.
- **Consumed by:** Nothing reads the census. It protects the owner's stated constraint that the site stays
  prerendered, and the Hobby plan's invocation budget on a project that has already been rate-limited for 24
  hours after a busy merge day.
- **Evidence:** measured in this repository — a build probe on 2026-09-12 produced `○ /llms.txt` with
  `export const dynamic = 'force-static'` and `ƒ /llms-full.txt` without it, every other route unchanged, so one
  missing line is the whole failure mode. Vendor-documented that it is silent: Next changed the default caching
  for GET handlers from static to dynamic in v15.0.0-RC
  (nextjs.org/docs/app/api-reference/file-conventions/route, version 16.3.5, lastUpdated 2026-04-30). All nine
  page routes carried `x-nextjs-prerender: 1` when re-checked on 2026-09-12.
- **Done when:** The header loop prints `1` for every page route and every endpoint, `0` for `/mcp` alone, and
  the build gate exits 0 with its route table pasted in the issue.

### The generated-representation walk: `/index.md` twins, `/llms.txt`, the JSON, the feed

- **What:** For every route, `GET <route>/index.md` returns 200 with a `Content-Type` starting
  `text/markdown`, its body carries the route's headings as sentences and the case study's stack rows as a
  Markdown table, and the route's served HTML advertises it with exactly one
  `<link rel="alternate" type="text/markdown">` whose href resolves to that 200. `/llms.txt` returns 200 as
  `text/plain; charset=utf-8` and parses as llmstxt.org v2. The JSON representation returns
  `application/json`, parses, and its array length equals the number of entries in
  `apps/web/src/data/case-studies.ts`. The feed returns `application/atom+xml; charset=utf-8` and satisfies
  RFC 4287's required elements under a real XML parser.
- **Consumed by:** The twins — OpenAI's Codex CLI via `rel="alternate"` discovery, anyone handed the URL, and
  the `Accept: text/markdown` clients (Claude Code, Cursor, the Copilot family, OpenCode) at the canonical URL,
  through the negotiation #59 ships. ChatGPT browse, the Claude.ai web app, Gemini and Perplexity fetch
  HTML only, so none of this is a citation channel. `/llms.txt`: **nothing reads it by default.** The JSON: any
  agent with a generic fetch tool, which is every agent. The feed: Google Feedfetcher and ordinary feed readers.
- **Evidence:** measured for the twins — acceptmarkdown.com's matrix reads Accept headers from live access logs,
  last updated 2026-06-22, with per-agent verification dates. Measured non-consumption for `/llms.txt` —
  Ahrefs' log study of 137,210 domains, 2026-06-15, found 97% of valid files fetched zero times in May 2026, and
  of the bots that read one, 77% were not AI tools at all; AI retrieval bots were 1.1% of requests.
  Vendor-documented that it is irrelevant to Search — Google's AI optimization guide, updated 2026-07-10: no
  machine-readable files, AI text files, markup or Markdown are needed to appear in Google Search. Formal
  standard for the media type (RFC 7763, March 2016, `charset` required) and for Atom (RFC 4287).
- **Done when:** Every twin, the `llms.txt`, the JSON and the feed answer with the right status, the right
  `Content-Type` and content that matches the data module, and every advertised href resolves to a 200. An
  advertised 404 fails this measure: it wastes the context of the one agent that looks.

### Google's own renderer: the two rich results, the blocked-resource list, and the schema validator

- **What:** Run Google's Rich Results Test by hand against the three case studies and `/about`; record that the
  Article family and Breadcrumbs are detected on the case studies and ProfilePage on `/about`, each with zero
  errors, and that the tool's page-resources list shows nothing blocked by robots.txt. Then the scriptable
  sibling: POST each route to `validator.schema.org/validate` with `url=`, strip the `)]}'` XSSI prefix, and
  assert `totalNumErrors === 0` — advisory, fail-open.
- **Consumed by:** Google Search consumes the markup, for the two rich results and for entity resolution. The
  Rich Results Test and validator.schema.org are checkers, not consumers: passing them is not evidence that any
  engine did anything. Neither is evidence of citation.
- **Evidence:** vendor-documented that the features are live — Breadcrumb and Article are in Google's
  structured-data gallery (updated 2026-06-15) and their references were updated 2026-09-08; ProfilePage's
  documented job is entity understanding and author linkage, not a visible SERP change. Measured that the tool
  cannot be automated: POST to `search.google.com/test/rich-results/result` returned 405 and GET returned the
  single-page-app shell, probed 2026-09-12. Measured that the validator works against this site: HTTP 200, the
  `)]}'` prefix, `totalNumErrors: 0`, `isRendered: true`, both existing nodes found, 2026-09-12.
  **Speculative as a citation lever, and the research contradicts the usual claim:** Google states structured
  data is not required for generative AI search and that there is no special schema.org markup to add, and
  Ahrefs' matched difference-in-differences over 1,885 pages found no citation lift from adding JSON-LD. Do not
  claim a knowledge panel: there is no Person rich result and no Google document describes markup as a route
  into the Knowledge Graph.
- **Done when:** Four Rich Results Test verdicts with zero errors and an empty blocked-resources list are pasted
  in the issue, and the validator reports zero errors on every route or its non-2xx is recorded as a
  third-party outage rather than a defect.

### The MCP round trip over streamable HTTP

- **What:** POST `tools/list` and `server/discover` to `https://miloscvetkovic.dev/mcp` with the headers spec
  revision 2026-07-28 requires, and assert a JSON-RPC result carrying the read-only tools, no `Mcp-Session-Id`
  response header, and `resultType: "complete"`. Then the negative cases: `GET /mcp` answers 405, a present and
  unknown `Origin` answers 403, a header/body protocol-version mismatch answers 400 with JSON-RPC `-32020`, and
  the deprecated HTTP+SSE path is not served. Finally, one `tools/call` round trip, and the published Claude Code
  connector snippet used unedited.
- **Consumed by:** A human who pastes the URL into Claude Code, a Claude custom connector, Cursor or VS Code —
  people who already decided to look at this site. **Nothing discovers it automatically:** SEP-2127 server cards
  were still an open pull request on 2026-09-11, the official registry states it is not intended to be consumed
  directly by host applications, and Anthropic's Connectors Directory submission portal requires a Team or
  Enterprise organisation.
- **Evidence:** formal standard for the protocol (modelcontextprotocol.io specification revision 2026-07-28:
  stateless, no `initialize` handshake, no `Mcp-Session-Id`, mandatory `server/discover`, required
  `MCP-Protocol-Version` / `Mcp-Method` / `Mcp-Name` headers, `Origin` MUST be validated, clients MUST send
  `Accept: application/json, text/event-stream`). **Speculative for any reach**, and the honest reason this
  endpoint exists is that it demonstrates the owner's engineering — protocol-current, stateless, no session
  store — not that it brings traffic or citations. Its realistic audience is smaller than a single `og:image`.
- **Done when:** Both RPCs answer correctly, all four negative cases behave, one `tools/call` returns grounded
  case-study content, and the snippet worked with no edit.

**The extraction loop (AC 5, 6).** Call the extractor #55 exports from its no-JavaScript spec rather than
writing a second one — the same HTML measured three ways on 2026-09-12 gave 4,623, 5,156 and ~5,249 characters,
and the difference was entirely the extraction. Run it twice per route, once with each tag-join convention:

```bash
# Token from OpenAI's own crawler page; the full string it publishes carries a +https://openai.com/ URL.
ua='GPTBot/1.4'
for r in "${routes[@]}"; do
  html="$(curl -sS -A "$ua" "https://miloscvetkovic.dev$r")"

    printf '%s' "$html" | node -e '<#55 extractor, joinTags = process.argv[1]>' "$join"

```

Both conventions are real. Chrome's `innerText` and a zero-separator strip reassemble `Most bugs live in the
gap`; a strip that inserts whitespace at tag boundaries does not, and Chromium's own accessibility tree names
those `h2`s letter by letter (274 per-character spans measured on the live page, 2026-09-12). The phrase
assertions pass because task #47 adds a contiguous visually-hidden copy beside the `aria-hidden` split copy —
not because the spans were removed. They must still be there: the scrolled axe pass counts them against a floor,
and the PRD forbids weakening a gate.

**Parsing `/llms.txt` as v2 (AC 8).** The spec (llmstxt.org, modified 2026-08-10) requires one H1 as the only
required section, then a blockquote summary, then free-form Markdown with no headings, then zero or more `##`
sections whose bodies are `[name](url)` lists optionally followed by `: notes`. v2 removed the special meaning
of the `Optional` section, so a file that still uses it is v1-shaped. Lighthouse's own rules, read from
`core/audits/agentic/llms-txt.js` at v13.4.1 on 2026-09-12, are narrower: `/^\s*#\s+.+/m`, `/\[.+\]\(.+\)/` and
a 50-character floor, with a 4xx returning `notApplicable` and a 5xx scoring 0 — so a broken file is strictly
worse than none, which is why this criterion parses the file itself rather than trusting the audit.

**The MCP POST (AC 14).** Revision 2026-07-28 requires `MCP-Protocol-Version` matching the body's `_meta`,
`Mcp-Method`, and `Mcp-Name` on `tools/call`, `resources/read` and `prompts/get`; clients MUST send
`Accept: application/json, text/event-stream`; servers MUST validate `Origin`. Build the body from the fixture
#62's unit test uses rather than hand-writing the `_meta` block, so the request this criterion sends and
the one the unit test asserts on cannot drift:

```bash
curl -sS -D- -X POST https://miloscvetkovic.dev/mcp \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -H 'MCP-Protocol-Version: 2026-07-28' \
  -H 'Mcp-Method: tools/list' \
  -H 'Origin: https://miloscvetkovic.dev' \
  --data @"$(node -e '<print #62 tools/list fixture to a temp file>')"
```

**Next.js 16 specifics, with the traps named.**

- Route handlers are **not** static by default. Next changed the default caching for GET handlers from static to
  dynamic in v15.0.0-RC, so a handler with no `export const dynamic = 'force-static'` becomes a serverless
  function — verified in this repository on 2026-09-12: `○ /llms.txt` with the export, `ƒ /llms-full.txt`
  without it, every other route unchanged. The failure is silent: the endpoint still answers. AC 4 is what
  catches it, from both sides — the `x-nextjs-prerender: 1` header on the host and the `.body` census in the
  build output.
- `force-static` is **removed** when `cacheComponents` is enabled (Next 16.0.0), along with `dynamicParams`,
  `revalidate` and `fetchCache`. This repository does not set `cacheComponents`, so every endpoint's export is
  valid today; adopting Cache Components later would break all of them and they would need `'use cache'`
  instead. If a future run finds an endpoint answering without the prerender header, check `next.config.ts` for
  `cacheComponents` before blaming the handler.
- `[slug].md` cannot work: a folder named `[slug].md` is a **literal** segment, and Next's generated validator
  types the handler as `RouteHandlerConfig<"/work/[slug].md">` with `params: Promise<{}>` — zero params, failing
  typecheck with `Property 'slug' is missing` (build probe, 2026-09-12). That is why the twins are
  `/work/<slug>/index.md`, produced by `generateStaticParams()` inside the route handler, and why AC 7 builds
  the twin path as `${route}/index.md` for every route including the flat ones.
- A prerendered handler's `.meta` file records the exact status and headers set in code, and `Content-Type`
  survives verbatim — `text/markdown; charset=utf-8`, `text/plain; charset=utf-8` and
  `application/atom+xml; charset=utf-8` all round-tripped untouched in the probe. So a wrong `Content-Type` in
  production is a code defect, never a platform one.
- ADR 0015 fixes the case-study slugs at build time: a slug absent from `generateStaticParams` 404s at the
  router. A twin for a case study added without a rebuild therefore 404s, which is correct for a static
  deployment and is what AC 7 would report.

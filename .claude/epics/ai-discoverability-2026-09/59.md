# Task: Markdown twins for every route, from one shared serialiser

## Description

A machine that fetches this site gets one representation: HTML whose animated headings are rendered
one `<span>` per character. The sentence "Most bugs live in the gap between what you asked for and
what you meant." is in the served bytes, but it is split across hundreds of elements, so whether a
reader sees a sentence or `M o s t  b u g s` depends entirely on how its extractor joins tag
boundaries. The home page's `h1` has the same shape in miniature: its two lines are separated by a
`<br />`, so plain text extraction reads `This happened at 3am.Nobody woke up.` with no space
(measured on the live site, 2026-09-12). This task adds a second representation where none of that
can happen — a Markdown twin per route at a uniform `/index.md` path, generated at build time from
one serialiser over the data modules — and advertises each twin from its page's `<head>`. It is
worth doing for three reasons and not for a fourth: OpenAI's Codex CLI is a documented consumer of
the discovery link; a generated twin is extraction insurance that does not depend on any extractor's
whitespace policy; and it is the substrate #60, #61 and #62 all render from, so building it
once removes three copies of the same facts. The fourth reason does not exist: ChatGPT, Claude.ai,
Gemini and Perplexity fetch HTML only, so no twin here is a citation channel, and Google states no
Markdown is needed to appear in Search. These are also the repository's first route handlers, which
makes one sentence in CLAUDE.md false; this task fixes that line and records the pattern in an ADR.

Branch: feat/markdown-twins. Lands as 2 PRs, squash-merged.

## Measures

### A `/index.md` Markdown twin for all nine routes, prerendered

- **What:** seven `route.ts` files producing nine URLs — `/index.md`, `/about/index.md`,
  `/blog/index.md`, `/contact/index.md`, `/skills/index.md`, `/work/index.md`, and
  `/work/<slug>/index.md` for the three case studies from one handler with its own
  `generateStaticParams()`. Every file carries `export const dynamic = 'force-static'`; the
  case-study handler also carries `export const dynamicParams = false`. Every body comes from the
  serialiser below and is returned through one shared `markdownResponse()` helper so the
  `Content-Type: text/markdown; charset=utf-8` is written in exactly one place. Each twin opens with
  an `# H1`, a summary paragraph, and a `Source:` line carrying the absolute canonical URL of the
  HTML page it mirrors.
- **Consumed by:** OpenAI's Codex CLI, which searches the initial HTML response for
  `<link rel="alternate" type="text/markdown">` and then fetches it; anyone handed the URL (from task
  #60's `/llms.txt`, or from the advertised link); and - through the content-negotiation measure below -
  Claude Code, Cursor, GitHub Copilot Chat, Copilot CLI, Microsoft Copilot and OpenCode, which send
  `Accept: text/markdown` to the canonical URL. The answer engines read nothing here: ChatGPT browse,
  Claude.ai, Gemini and Perplexity fetch HTML only.
- **Evidence:** measured for consumption — acceptmarkdown.com's agent matrix, which reads `Accept`
  headers from a live server's access logs, last updated 2026-06-22, with the HTML-only list each
  verified 2026-04-18. Measured for the mechanism — a build probe of this repository on 2026-09-12
  (next 16.3.4): a handler with `force-static` printed `○`, a byte-identical handler without it
  printed `ƒ` and emitted no response file, and `/work/[slug]/index.md` with `generateStaticParams`
  printed `●` three times with `content-type: text/markdown; charset=utf-8` round-tripping
  untouched. Vendor-documented for the shape — llmstxt.org v2 (modified 2026-08-10) blesses both
  `page.md` and `page.html.md`, and RFC 7763 (March 2016) registers `text/markdown` with a required
  `charset`.
- **Done when:** all nine URLs answer 200 with `text/markdown; charset=utf-8`, each emits a
  prerendered response file under the build output, the build table shows no `ƒ`, and a path with no
  twin (`/nope/index.md`, `/work/does-not-exist/index.md`) still answers a true 404 rather than 200
  with HTML.

### One shared serialiser over the data modules

- **What:** a new module `apps/web/src/lib/serialise.ts`, beside the existing `theme.ts`, exporting
  `markdownTwinPath(routePath: string): string` (`'/'` → `/index.md`, `'/about'` →
  `/about/index.md`), `markdownResponse(body: string): Response`,
  `renderSections(sections: readonly PageSection[]): string`,
  `pageToMarkdown(page: PageRecord): string` and
  `caseStudyToMarkdown(caseStudy: CaseStudy): string`. It imports `caseStudies`, `getCaseStudy` and
  `formatMetric` from `@/data/case-studies` — so a twin's metric string is produced by the same
  function the page uses — and the page records from a new `@/data/pages` module. A case study's
  twin renders its title, the `datePublished` and `dateModified` #56 adds, the metric with the
  scope and window #56 adds, description, challenge, approach, contributions, impact and the
  tech stack as a two-column table. No route handler builds Markdown of its own.
- **Consumed by:** nothing outside the repository reads the module. Its consumers are internal and
  named: this task's nine twins, #60's `/llms.txt` and JSON representation, #61's Atom
  feed, #62's MCP tool payloads.
- **Evidence:** convention-only, and the convention is this repository's own — CLAUDE.md makes
  `case-studies.ts` the single source of truth for project copy, metrics and tech stacks, and the
  epic fixes "one serialiser, one source" as a non-negotiable. The external evidence is negative and
  worth stating: the drift a hand-written machine-readable file accumulates is the failure mode
  Ahrefs' 2026-06-15 study describes, where a file with an authoritative shape hands agents stale
  facts.
- **Done when:** `pnpm --filter web exec vitest run src/lib/__tests__/serialise.test.ts` passes with
  assertions that every field of every case study appears in its twin, and no `route.ts` in the app
  contains Markdown syntax.

### `alternates.types` on every route, added inside #48's metadata helper

- **What:** one change in the shared metadata helper #48 lands at `apps/web/src/lib/metadata.ts`
  (`pageMetadata({ path, title, description, … })` in #48's task file; the PRD calls it
  `mergeMetadata`): alongside the `alternates.canonical` it already sets, it adds
  `types: { 'text/markdown': markdownTwinPath(path) }`. Because every route's metadata goes through

  cannot diverge. The relative value resolves against the `metadataBase` already set at
  `apps/web/src/app/layout.tsx:26`.
- **Consumed by:** exactly one documented client — OpenAI's Codex CLI. Nothing else in the agent
  matrix does discovery this way, and `rel="describedby"` (the v2 sibling pointing at `llms.txt`)
  has no documented consumer at all, which is #60's problem, not this one.
- **Evidence:** measured — acceptmarkdown.com records Codex CLI's behaviour (2026-06-22), and a
  build probe of this repository on 2026-09-12 emitted
  `<link rel="alternate" type="text/markdown" href="…"/>` as an absolute URL from exactly this
  metadata shape. Vendor convention for the practice: Vercel's own documentation pages advertise
  their Markdown twins the same way (vercel.com/docs/agent-resources/markdown-access, last updated
  2026-09-03).
- **Done when:** every route's served HTML carries exactly one
  `link[rel=alternate][type="text/markdown"]`, its `href` answers 200 with `text/markdown`, and

### Content negotiation on `Accept: text/markdown`, so the clients that ask actually get it

- **What:** a `beforeFiles` rewrite in `apps/web/next.config.ts` matching the `accept` request header
  and rewriting to the twin, so the canonical URL returns Markdown to a client that prefers it and HTML
  to everyone else. One rule per known route plus a dedicated rule for `/` (which otherwise rewrites to
  `/.md` and 404s), scoped to the nine routes rather than `/:path*` - a broad source turns every
  markdown-preferring request for a path with no twin, `/_next/*` assets included, into a 404. The
  responses also carry `Vary: Accept`.
- **Consumed by:** the clients that send the header and would otherwise never reach a twin: Claude Code,
  Cursor, GitHub Copilot Chat, Copilot CLI, Microsoft Copilot and OpenCode. This measure is what makes
  US-3 true for them; without it they request Markdown at the canonical URL and receive HTML.
- **Evidence:** measured in this repository - a build probe on 2026-09-12 added exactly this rewrite and
  found every route still `○`/`●` with no function added, `curl -H 'Accept: text/html' /about` returning
  `text/html` and `curl -H 'Accept: text/markdown, text/html, */*' /about` returning
  `text/markdown; charset=utf-8`, both `x-nextjs-cache: HIT`. Vendor-documented as the pattern:
  vercel.com/docs/agent-resources/markdown-access (last updated 2026-09-03). Vercel's CDN already keys
  its cache on `Accept`, so `Vary: Accept` is for third-party and client caches rather than for
  correctness here.
- **Note on the research disagreement:** one researcher advised against negotiation on the grounds that
  App Router needs `middleware.ts` for it, which would end the static posture. That premise does not hold
  for the rewrite: the routing layer handles it with no middleware and no function, which the probe above
  confirms. The middleware objection stands only for negotiating inside a Server Component.
- **Done when:** both representations answer from every canonical route URL by `Accept` alone, the build
  output still shows no function, `/` serves Markdown with the header, a path with no twin still serves
  its normal 404 to a markdown-preferring client, and an e2e case asserts all of it.

## Technical Details

**The route-handler trap, and why one export is load-bearing.** Since Next 15.0.0-RC the default
caching for `GET` route handlers is _dynamic_, so a handler that returns a constant string becomes a
server function unless it exports `dynamic = 'force-static'`
(`nextjs.org/docs/app/api-reference/file-conventions/route`, 16.3.5, lastUpdated 2026-04-30, Version
History). This was measured in this repository on 2026-09-12 (next 16.3.4): two byte-identical
handlers, one with the export and one without, printed `○` and `ƒ` respectively, and only the first
emitted a prerendered response. With the export, Next writes the response body and a metadata file
at build time and the `Content-Type` survives verbatim; `cookies()`, `headers()` and
`useSearchParams()` return empty values, which is correct for a content endpoint
(`nextjs.org/docs/app/guides/caching-without-cache-components`, 16.3.5, lastUpdated 2026-08-25).

**`force-static` is removed only under Cache Components.** It is absent from the main
route-segment-config options table, which reads like removal, and it is fully documented in the
"Caching (Previous Model)" guide. The removal applies when `cacheComponents: true` is enabled
(`route-segment-config`, Version History `v16.0.0`). `apps/web/next.config.ts:33-43` does not set
`cacheComponents`, so `force-static` is the correct mechanism today. Adopting Cache Components later
breaks every endpoint in this epic, which needs `'use cache'` instead — the ADR records this so the
upgrade is not a surprise.

**`[slug].md` cannot work.** A folder named `[slug].md` is a _literal_ segment, not a dynamic one:
Next's generated validator types the handler as `RouteHandlerConfig<"/work/[slug].md">` with
`params: Promise<{}>`, and a build probe on 2026-09-12 failed typecheck with
`Property 'slug' is missing`. There is no partial-dynamic-segment mechanism, which is why the
owner's uniform `/index.md` decision is the only shape that covers the case studies as well as the
flat routes. The probe verified the two ends of that shape: `app/about.md/route.ts` coexisting with
`app/about/page.tsx` (both `○`, distinct content types) and `app/work/[slug]/index.md/route.ts` with
its own `generateStaticParams()` (`●` ×3). It did **not** probe
`app/index.md/route.ts` or `app/about/index.md/route.ts`; those are the same literal-segment
mechanism, and the first thing to confirm on PR 2 is that the build table lists them, before any
further handler is written.

**`generateStaticParams` inside a route handler** is supported, and with `dynamicParams = false` it
prerenders one response per param and 404s everything else, with no function in the output
(`nextjs.org/docs/app/api-reference/functions/generate-static-params`, 16.3.5, lastUpdated
2026-08-25; build probe 2026-09-12). Mirror the page: `apps/web/src/app/work/[slug]/page.tsx:17`
sets `dynamicParams = false` and `:19-23` returns `caseStudies.map(({ slug }) => ({ slug }))`, for
the reasons in ADR 0015. The twin handler uses the same list and the same flag, so an unknown slug
is a routing-level 404 in both representations. Under Cache Components `generateStaticParams` must
return at least one param and `dynamicParams` is itself removed — recorded in the ADR with the
above.

**Content type and the response helper.** `text/markdown; charset=utf-8`, with the charset required
by RFC 7763 (March 2016). Return it from one `markdownResponse()` in the serialiser rather than in
seven handlers, so a copy-paste cannot produce a twin served as `text/plain`. Each handler is then
three lines: the `force-static` export, an import, and a `GET` that returns
`markdownResponse(pageToMarkdown(pages['/about']))`.

**Absolute URLs inside the bodies.** The `Source:` line needs an absolute URL, which
`metadataBase` cannot supply to a plain-text body. Resolve it once in the serialiser the way
`apps/web/src/app/sitemap.ts:5` and `apps/web/src/app/robots.ts:4` already do
(`process.env.NEXT_PUBLIC_SITE_URL || 'https://miloscvetkovic.dev'`). This means a preview
deployment's twins name production URLs — exactly what the sitemap already does, and Vercel marks
previews `noindex`, so it is a pre-existing behaviour rather than a new defect. Do not invent a
second origin resolution.

**Where the copy comes from, and who owns each record.** `apps/web/src/data/pages.ts` is new and
holds one record per static route: `path`, `title`, `summary`, `sections`. `PageSection` needs three
variants and no more, because that is the shape of the content on the pages: a heading with prose
paragraphs, a heading with a list of `{ term, description }` entries, and a heading with a table
(`columns` plus `rows`). It is filled from text that already lives in a module or that this task
moves — the home story's six closing pairs (`discovery-phase.tsx:183-190`,
`strategy-phase.tsx:331-338`, `execution-phase.tsx:352-359`, `gauntlet-phase.tsx:305-312`,
`loop-phase.tsx:246-253`, `game-complete.tsx:120-127`), the `title` and `description` each route
passes to #48's helper, the content consts inside `/about`, `/skills` and `/contact` with the
section headings and paragraphs around them and `/blog`'s stub copy (the Measures name each const
and its lines), and for `/work/<slug>` nothing new at all, because `caseStudies` already holds it —
`/work`'s record carries only its own section headings and reads the studies from there.

**This task ships all six page records complete**, every section heading, row and paragraph its page
renders, rather than shipping four thin ones and handing the rest to #58. The two tasks are
both `parallel: true` and neither blocks the other, so a record left for another task to finish can
stay unfinished, and a twin that is permanently thinner than its page is the one failure this task
exists to prevent. What keeps the records complete afterwards is a gate rather than a promise: AC
14's parity spec fails when one of those four pages renders a heading or a table row its record does
not carry. So #58's tables and its question-and-answer block carry their copy in the record,
where the serialiser already reads it and where the epic's one-source rule and CLAUDE.md put data
anyway — #58's own Dev Notes already send its copy there, "where pages already read it, and no
fact is written twice" — and #58's row-count assertions and the twin's rows then come from one
array. Task #61 does the
same for `/blog` when it lands its post model; until then that record holds the stub copy the page
shows today. The move lands in PR 1 beside the serialiser, so PR 2's handlers render records that are
already complete.

**The overlap with #57 and #58, and who rebases.** Moving those consts means this task edits

**Deliberately not done here, with the evidence.**

- **`Accept: text/markdown` content negotiation on the canonical URLs.** Not shipped, and this is
  the choice that costs the most reach, so it is recorded rather than hidden. Three reasons. The
  `next.config.ts` `beforeFiles` rewrite form stays fully static — verified in this repository on
  2026-09-12, every route still `○`/`●` — but it "doesn't honor `q=0` rejections" and does not rank
  by q-value (acceptmarkdown.com/recipes/nextjs), so it is not negotiation; a broad `source` turns
  every path without a twin into a 404 for Markdown-preferring clients, and `/` needs its own rule
  because `/:path*` maps it to `/.md`, which the probe measured as a 404; and the middleware form
  that would honour q-values puts a function in front of all nine prerendered routes, against the
  epic's static rule. The consequence is stated in the Measures: the `Accept`-header agents reach a
  twin only through discovery. Revisit when a client that matters is observed asking for Markdown
  and refusing to follow `rel="alternate"`.
- **Emitting the twins into `public/` from a prebuild script.** It would allow `/work/<slug>.md`,
  which route handlers cannot. Rejected: generated `.md` files inside the project are rewritten by
  the repository's PostToolUse Prettier hook, would need adding to `.gitignore`, `.prettierignore`
  and `.vercelignore` — the seven-places problem CLAUDE.md already documents for `.next-e2e` — and
  nothing would typecheck them against `case-studies.ts`.
- **`llms-full.txt`** (out of scope, PRD): not in the llms.txt specification at all, and the
  published examples have scaled themselves past any context window (50.8 MB at one vendor, 34.3 MB
  at another, measured 2026-09-12). This site's whole content source is about 12 KB, so the twins
  plus #60's `/llms.txt` are already the full text.
- **An `AGENTS.md` at the site root** (out of scope, PRD, as `/.well-known/agent-skills`'s
  neighbour): a repository convention with no HTTP serving story and no client that fetches it;
  agents.md documents none, and the 200s in the wild are soft 404s (measured 2026-09-12). It is also
  imperative text addressed to agents, published at a URL — a prompt-injection surface with no
  reader.
- **`X-Robots-Tag: noindex` on the twins.** Not set. They are duplicate content of the HTML, and the
  canonical tag #48 ships is what makes the HTML primary; Google states such files "will neither
  harm nor help" visibility (`developers.google.com/search/docs/fundamentals/ai-optimization-guide`,
  updated 2026-07-10), so a `noindex` would only risk discouraging the readers this is for.
- **`.md` URLs in the sitemap.** The sitemap stays canonical HTML; discovery is the link relation.
- **A cache policy for the twins.** Next's default on a prerendered handler is
  `s-maxage=31536000`, and on Vercel `s-maxage` is stripped before the response reaches the client,
  so browsers and agents get no caching. Whether a `next.config.ts` `headers()` rule even applies to
  a prerendered handler on Vercel is an open question from the research, untested outside
  `next start`. Not decided here: `headers()` belongs to #48's PR 3, and #64 measures the real
  response headers on production before anyone tunes them.

**Owner decisions that apply.** Uniform `/index.md` for every route, including the flat ones — that
is what makes the seven handlers look asymmetric on disk and uniform on the wire. Dates and metric
windows are placeholders that fail CI until the owner fills them in review (#56 owns the gate);
the serialiser renders whatever those fields hold, so a placeholder cannot ship quietly through a
twin. Content is drafted by Claude and edited by the owner: nothing in `pages.ts` may be newly
written prose — every string in it is text already on the site.

**Needs the owner at execution time.** Nothing blocking. One judgement call to confirm during
review: whether `/blog/index.md` ships while `/blog` is still a placeholder. The uniform decision
says yes and the twin honestly says there are no posts yet; #60 must still keep `/blog` out of
`/llms.txt` until #61 lands a post, because a link that leads nowhere teaches an agent the file
is unreliable.

**Two repository traps to expect.** Adding seven route handlers changes the generated route types,
and `apps/web/tsconfig.json` compiles the copy in `.next-e2e`, which only an e2e run refreshes: if
`pnpm typecheck` disagrees with CI about the new routes, run
`pnpm --filter web exec rm -rf .next-e2e`. And `docs/adr/README.md` gains a row from #57, #59,
#62 and #63 — take the ADR number last, rebase, and re-run `pnpm format`.

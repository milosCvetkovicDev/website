# Task: Content shape: headings that name the subject, tables, and metrics with a scope

## Description

A machine reading this site cannot learn from its headings who the site is about or what it covers:
five of seven `H1`s are narrative hooks that name neither the person nor the subject — `/` says "This
happened at 3am. Nobody woke up.", `/skills` says "Tools are just tools." It cannot read the tech
stacks or the career timeline as data either, because there is not one `<table>` element anywhere on
the site while the content is almost entirely tabular. And it cannot quote a single metric safely:
"73%" appears with no denominator, no period and no definition of what was counted. This task
rewrites those five `H1`s so each names the person or the subject, keeping every hook as display copy
in a paragraph directly beneath it; converts the case-study tech stacks, the About timeline, the
About quick facts and the `/skills` toolkit grid into real tables with captions and header cells;
renders each metric's scope and measurement window in the visible text; and adds a visible
question-and-answer block whose value is the visible pattern, not markup. It is worth doing because
this is the only area of the epic with controlled measurement behind it — the KDD 2024 GEO benchmark
scored statistics at +37% and cited sources at +30% for generative-engine visibility while keyword
stuffing scored −9% — and because every fact worth citing has to live in rendered text: the measured
evidence says visible HTML is what extractors read, and JSON-LD is not a citation lever. Claude
drafts every line below; the owner edits before merge, and nothing ships in the owner's voice
unreviewed.

Branch: feat/content-shape-for-extraction. Lands as 3 PRs, squash-merged.

## Measures

### Every visible metric states its scope and its measurement window

- **What:** Each figure the site shows gets a visible basis: what was counted, against what
  baseline, over what period. On the case studies this renders the metric basis field task #49
  introduces plus the measurement window #56 adds, as one line under the metric. On `/about` the
  four quick facts gain a basis column. On `/work` the stats bar's "100% In Production" becomes a
  figure derived from the case-study statuses ("3 of 3 running in production") and "0 Left
  Unfinished" is dropped or given a denominator. On `/skills` the proficiency bars gain one line
  saying they are self-assessed rather than measured. Drafted lines are in Technical Details; every
  number the owner must supply is written with #56's `ownerTodo('<what the owner supplies>')`
  marker helper — never the bare `OWNER_TODO` constant, which is that task's typed union state and
  not how a marker inside a sentence is spelled — and takes a row in its `unfilledOwnerFields`
  register. The checker walks only the sources registered with it, so this task also adds its own
  `{ id, value }` entry to that source array; without the entry the gate would silently cover
  nothing. It then fails while a marker is unregistered, while a row is stale, or while a row is past
  its owner-set deadline, and no code path can print a marker: the consumer omits the whole sentence,
  cell or row while the marker survives.
- **Consumed by:** Generative engines, per the benchmark below — and human readers, who are the
  audience that actually hires. Nothing consumes a bare percentage as a citable claim; an unsourced
  number is a credibility cost with a person and an unquotable fragment for a model.
- **Evidence:** measured — KDD 2024 GEO benchmark (arXiv 2311.09735, submitted 2023-11-16, revised
  2024-06-28): Statistics Addition +37%, Cite Sources +30%, Keyword Stuffing −9% relative visibility
  in generative engines. This is an academic benchmark against generative engines, not a vendor
  statement about production behaviour, and it predates every 2026 engine version: treat the
  direction as supported and the magnitude as unknown. The 2026 follow-ups agree in direction only
  (FeatGEO, arXiv 2604.19113, 2026-04-21: document-level properties dominate lexical edits; AgentGEO,
  arXiv 2603.09296, 2026-03-10: targeted repairs beat generic rewriting).
- **Done when:** Every figure rendered on `/`, `/about`, `/work`, `/work/<slug>` and `/skills` either
  states what it counted and over what period in visible text, or is removed; no route's served HTML
  contains `OWNER-TODO`, every marker still in the data carries a register row with an owner-set
  `expires`, and the module holding this task's markers is one entry in the checker's source array,
  proved by #56's checker under `pnpm test`; and a reviewer can answer
  "a percentage of what, measured when?" for every number on the page without leaving it.

### Five `H1`s name the person or the subject, and the hook stays as display copy

- **What:** `/`, `/about`, `/work`, `/skills` and `/contact` get a short descriptive `H1`; the
  existing hook moves into a `<p>` directly beneath with the same display styling, so the voice and
  the visual hierarchy survive. Exact drafted lines are in Technical Details. `/work/<slug>`
  (the case-study title) and `/blog` ("Writing") already name their subject and are left alone —
  `/blog`'s copy belongs to #61, which lands the posts. This is a semantics fix, not a count
  fix: every route already serves exactly one `H1`, and Google's position is that heading counts do
  not matter.
- **Consumed by:** Google (documented use of headings to understand the context of page sections);
  Microsoft/Copilot, which names "clear headings" in writing; and every extraction pipeline, since
  visible headings and the text under them are the one thing measured to be reliably extracted.
- **Evidence:** vendor-documented for the mechanism — Bing Webmaster Tools AI Performance
  announcement, 2026-02-10 ("Clear headings, tables, and FAQ sections help surface key information
  and make content easier for AI systems to reference accurately"); Google's Mueller on headings via
  Search Engine Journal (secondary, quoting Google directly). The magnitude of the effect is
  unmeasured, and no vendor promises a ranking or citation change from a heading rewrite.
- **Done when:** Each of the five routes serves an `H1` that contains the person's name or the
  route's subject, each hook string is still present in the served HTML as a paragraph, every `H1` is
  unique across routes and non-empty, and no `H1` is a keyword list.

### The tech stacks, the timeline, the quick facts and the toolkit grid become real tables

- **What:** Four `div` grids become `<table>` elements with a `<caption>`, `<th scope="col">` column
  headers and `<th scope="row">` row headers, keeping the Tailwind styling and wrapping each table in
  an `overflow-x-auto` container: the per-case-study tech stack, the `/about` career timeline, the
  `/about` quick facts, and the `/skills` "full toolkit" category grid. No data-model change —
  `techStack` is already `{ category, items[] }[]`, which is a two-column table rendered as something
  else.
- **Consumed by:** Microsoft/Copilot (the only vendor to state a format preference in writing) and
  every HTML-to-Markdown converter in every extraction pipeline: a `<table>` converts to a Markdown
  table with its rows intact, while a grid of `<div>`s collapses into an ambiguous run of words.
- **Evidence:** vendor-documented for the preference (Bing Webmaster Tools AI Performance, 2026-02-10)
  plus a mechanical certainty for the conversion — converters preserve table rows by construction;
  that is not a measured citation lever and must not be written up as one. Measured locally
  2026-09-12: zero `<table>` elements in the live HTML of all seven routes.
- **Done when:** The served HTML of `/work/<slug>`, `/about` and `/skills` contains the four tables,
  each with a caption and header cells, with one row per data entry; the axe gate stays green with
  its table rules running; and the page body never scrolls horizontally at 375px.

### A visible question-and-answer block on /about, with no FAQPage markup

- **What:** Three questions a real visitor asks, each as an `<h2>` ending in a question mark followed
  by one self-contained answer paragraph of 40–80 words, drafted in Technical Details. A fourth
  question about availability is drafted with a placeholder because only the owner can answer it. No
  `FAQPage` JSON-LD, no `HowTo`, no `speakable`.
- **Consumed by:** Nothing reads it as structured data by default — that is the point. The visible
  pattern (a question-shaped heading with a short self-contained answer under it) is what an
  extractor can lift as a unit; Microsoft names "FAQ sections" in writing as helping AI systems
  reference content accurately.
- **Evidence:** vendor-documented for the visible pattern (Bing Webmaster Tools AI Performance,
  2026-02-10). The markup is dead: Google's FAQPage deprecation notice (added 2025-05-08) said the
  rich result would stop appearing on 2026-05-07, the documentation page was deleted 2026-06-15, and
  Rich Results Test and Search Console support followed in June 2026 with the API in August 2026.
  Anything claiming FAQPage markup is a cheap win in 2026 is recycling pre-deprecation advice.
- **Done when:** `/about` serves three `<h2>` questions, each followed by a 40–80 word answer
  paragraph, in the HTML with JavaScript disabled; `grep -rn 'FAQPage\|HowTo\|speakable' apps/web/src`
  prints nothing; and the answers restate no case-study metric literal (they reference, per
  CLAUDE.md's single-source rule).

### Sentence boundaries in the hero survive text extraction

- **What:** The hook's two lines are separated by `<br>` inside one element, so extracted text reads
  `This happened at 3am.Nobody woke up.` with no space. Give the boundary a real gap (separate block
  children, or a trailing space) so the extracted text reads as prose. Same check applied to the
  other multi-line hooks this task moves into paragraphs.
- **Consumed by:** Every non-rendering crawler that reads the served HTML — GPTBot, OAI-SearchBot,
  ClaudeBot, PerplexityBot — plus any HTML-to-text pipeline.
- **Evidence:** measured — local `curl` and Playwright (`javaScriptEnabled: false`) extraction of the
  live site on 2026-09-12 produced `This happened at 3am.Nobody woke up.` and
  `…what you meant.I close that gap…` from 5,156 characters of static body text. The related claim
  that per-character animation spans shatter headings into single letters is **not** supported: the
  same measurement found both Chrome's `innerText` and a plain tag-strip reassemble the words
  correctly, and the researcher attributes the `M o s t  b u g s` reading to their own extraction
  method. This task therefore touches no animation component and claims no extraction benefit there.
- **Done when:** A no-JavaScript extraction of `/` contains `This happened at 3am. Nobody woke up.`
  with the space, and no sentence boundary in the routes this task edits loses its whitespace.

## Technical Details

### The five `H1`s, drafted — every line is a draft for the owner to edit

The pattern is identical on each route: the descriptive line becomes the `<h1>`, the hook becomes a
`<p>` immediately beneath it carrying the hook's current display classes, so the hook stays the
visually dominant line and only the element changes. The `<h1>` takes a smaller display size.

- Each drafted line names a subject; none is a keyword list, because the one controlled measurement
  in this area scored keyword stuffing at −9% (KDD 2024). `/work`'s line deliberately mirrors that
  route's own `metadata.description` (`apps/web/src/app/work/page.tsx:8-9`) so the head and the
  heading agree. `/contact`'s line says exactly what the page provides: three profile links, no form
  and no address (`apps/web/src/app/contact/page.tsx:14-51`).
- `/` also carries a `sr-only` paragraph that names the person and the specialisation
  (`hero-content.tsx:138-141`). Once the `H1` says that visibly, the hidden paragraph is a duplicate:
  remove it and keep the fact visible, which is also what Google's structured-data policies push
  toward ("Don't mark up content that is not visible to readers of the page", sd-policies updated
  2026-07-10). `hero-content.test.tsx:40-47` asserts that paragraph exists and must be retargeted at
  the visible copy, not deleted.
- `/blog`'s `H1` is "Writing" (`apps/web/src/app/blog/page.tsx:17`) and `/work/<slug>`'s is the case
  study title (`apps/web/src/app/work/[slug]/page.tsx:87`). Both already name their subject; `/blog`
  belongs to #61, which lands posts and can strengthen the line with them.
- Element-tag changes can move a node in or out of a GSAP selector, and the repo's rule is that no
  animated text may rest at partial opacity. `/` is the route with the axe contrast-node floors
  (`apps/web/e2e/accessibility.spec.ts:140,149-152`), so run the console and accessibility gates and
  the story spec after the hero edit.

Accessibility specifics, checked against `apps/web/e2e/accessibility.spec.ts:90-138`: the gate selects
rules by the `wcag2a`/`wcag2aa` tags, so `th-has-data-cells` runs without a map entry and
`td-has-header` and `table-fake-caption` are both explicitly enabled at `:132-135` — real `<th>`
cells with valid `scope` values and a real `<caption>` (not a `<td>` acting as one) are required.
`scope-attr-valid` and `empty-table-header` are best-practice-only rules and
are **not** selected by those tags, so an invalid `scope` value will not be caught by the gate: get
it right by reading, not by running. `scrollable-region-focusable` is disabled at `:125`, so the gate
will also not catch a scroll container a keyboard user cannot reach — give each wrapper `tabindex={0}`
and an accessible name anyway, and confirm by keyboard during the screenshot pass. Style captions and
cells with `--muted` / `--accent-text` per ADR 0011; never dim text with an opacity modifier, and
never use a palette status class (ADR 0010).

### Next.js 16 specifics, and the traps that apply even though this task adds no endpoint

- This task adds **no** route handler and no dynamic API. That matters because route handlers are not
  static by default: since `v15.0.0-RC` the default caching for `GET` handlers is dynamic, so a
  handler without `export const dynamic = 'force-static'` becomes a serverless function
  (nextjs.org/docs/app/api-reference/file-conventions/route, 16.3.5, last updated 2026-04-30). Tasks
  #59–#61 add the first handlers in this repository and every one of them carries `force-static`; the
  MCP endpoint of #62 is the single permitted function.
- `force-static` is what keeps those responses prerendered — it forces `cookies()`, `headers()` and
  `useSearchParams()` to return empty values (nextjs.org/docs/app/guides/caching-without-cache-components,
  2026-08-25) — and it is **removed only when Cache Components is enabled**
  (route-segment-config version history, `v16.0.0`). Nobody on this task enables Cache Components.
- The rule this task must not break: touching a page's rendering so that it reads a dynamic API
  (`cookies()`, `headers()`, `searchParams`) opts that page out of prerendering silently — the page
  still works, it just stops being `○`/`●`. All four table conversions and the Q&A block stay server
  components with no data fetching, and `/work/[slug]` keeps `dynamicParams = false` with
  `generateStaticParams` (`apps/web/src/app/work/[slug]/page.tsx:17-23`, ADR 0015).
- `[slug].md` is impossible and is nobody's fallback: a folder named `[slug].md` is a literal segment,
  and Next's own generated validator types such a handler as `RouteHandlerConfig<"/work/[slug].md">`
  with `params: Promise<{}>` — zero params. The epic's uniform `/index.md` shape exists because of
  that; it is #59's concern, not this task's, and this task must not add a Markdown twin.

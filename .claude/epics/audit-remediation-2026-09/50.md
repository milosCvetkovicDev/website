# Task: Harden the CI gates, test harness and agent tooling

## Description

All seven CI gates are green, but several of them can pass without checking what they exist to check. The
allowBuilds drift gate skips itself and exits 0 when its script is run by a path that goes through a symlink, the
ADR 0009 layout-barrel lint catches one of four spellings of the same import, and nothing checks the commit
messages GitHub writes to `main` when it squashes a PR, so four commits there already break the project's own
convention. Around the gates, the test harness erodes trust in a green run: 12 jsdom errors on every `pnpm test`,
specs that interact before hydration, flaky retries whose traces are thrown away, server-side errors nobody reads,
assertions that would pass on broken code, and gate comments that point at superseded decisions. The agent tooling
has drifted too: every agent-run `next dev` writes an untracked `AGENTS.md`/`CLAUDE.md` pair into `apps/web` that
Claude Code then loads as instructions, every web build artifact in the turbo cache carries the dev server's
~400 MB output while `.env.local` is not hashed at all, the ui-reviewer agent predates the colour ADRs it is meant
to enforce, and every production build fails if Google Fonts cannot be reached. US-7 and FR-17 require a green gate
to mean its property holds, and every other task in this epic leans on these gates and this tooling.

Branch: ci/gate-hardening. Lands as five PRs, squash-merged.

**PR 1, commit messages (gates-v2, tooling-13).**

- New `.github/workflows/commitlint.yml` with one job named `Commit messages`. Keep the name stable: branch
  protection binds required checks to job display names, which is why the two `ci.yml` job names
  (`ci.yml:23`, `:64`) must not change either.
- Triggers: `pull_request` with `types: [opened, edited, synchronize, reopened]`, and `push` to `main`. A job-level
  `if` skips an `edited` event whose `github.event.changes.title` is empty, so a body edit does not re-run it.
- Steps: the same SHA-pinned checkout, pnpm and Node setup as `ci.yml:27-40` (checkout with `fetch-depth: 0`),
  then `pnpm install --frozen-lockfile`.
- On a PR: `printf '%s\n' "$PR_TITLE" | pnpm exec commitlint`, then
  `pnpm exec commitlint --from "$BASE_SHA" --to "$HEAD_SHA" --verbose`. The title and SHAs come in through `env:`
  from `github.event.pull_request`, never interpolated into `run:`, because a PR title is attacker-controlled
  input.
- On push: `pnpm exec commitlint --from HEAD~1 --to HEAD --verbose`.
- Workflow-level `permissions: contents: read`, and concurrency that cancels superseded PR runs only, as at
  `ci.yml:10-15`.
- Why a separate workflow rather than a step in the `quality` job: a title edit then re-runs only this job, not the
  build and e2e, and `ci.yml` keeps the seven gates the docs list.
- Dependabot: `body-max-line-length` is applied by `@commitlint/ensure`'s `max-line-length`, which exempts any line
  matching `\bhttps?://\S+`, so a bot body of long lines that each carry a URL passes. Pipe both open Dependabot
  PRs' messages through `pnpm exec commitlint` before merging the check, and if one fails, fix it in
  `commitlint.config.mjs` rather than exempting the bot.
- The four failing commits on `main` stay as they are; `main` is never rewritten or force-pushed.
- ADR 0004's Consequences call commitlint a local-only gate. That was true when it was accepted, so ADR 0012 gives
  no ground to correct it. Record the new check in CLAUDE.md's Quality gates and README's gate table; if it earns an
  ADR of its own, take the number at PR time.

# Task: Acceptance test baseline: RED tests for the verified defects and coverage for untested routes

## Description

The suite looks at two routes, on one desktop viewport, at rest, in the light scheme, and never
crosses a route boundary. Every defect this epic fixes sits outside that window: on a phone, in a
hover state, on the other eight routes, in the dark scheme, and in the served head that crawlers and
link previews read. The accessibility gate makes the blind spot worse by counting axe's `incomplete`
results as passes, so more than half of the at-rest text on the home page is unmeasured and the hero
island ships at 2.6:1 with four green axe tests. A gate that cannot fail is not evidence, and the
fixes in #46, #47, #48 and #49 would land with nothing to prove they worked or to stop them
regressing.

This task lands the measuring instrument before any fix. It adds two phone projects, extends the axe
gate to every route in both schemes with a recorded unresolved-contrast budget and hover/focus
passes, and adds e2e for navigation, the mobile menu, client-side navigation, theme persistence, the
SEO surface, the markup served with JavaScript off, the `/work` cards and the case-study, 404 and
error pages. Behaviour that already works lands as ordinary green tests so it cannot regress
unnoticed. Every verified defect that #46 to #49 remove lands as an expected failure naming
the task that fixes it and the manifest row it flips, so CI stays green today and the fixing pull
request has to delete the annotation — an unexpected pass fails the run. The task changes no file
under `apps/web/src` outside a `__tests__` folder, which is what keeps it out of the way of the four
tasks that depend on it.

Branch: test/audit-acceptance-baseline. Lands as 3 PRs, squash-merged.

## Technical Details

### RED test manifest

One row per expected-failure test. Each is a Playwright `test.fail()` or a Vitest `it.fails` whose
annotation names the fixing task, so CI is green today and the fixing pull request must delete the
annotation — both runners fail on a test that was expected to fail and passed.

The ID column is the label the fixing tasks cite as their stop condition: #46 owns R1 to R11,
#47 owns R12 to R21, #48 owns R22 to R32 and #49 owns R33 to R39. Each annotation
carries its row ID alongside the task, so a row keeps its identity if the wording of the assertion
changes; IDs are never reused or renumbered once this task is synced.

### Implementation approach

- **Projects.** `apps/web/playwright.config.ts:51` becomes three projects. The desktop `chromium`
  project takes `testIgnore: /mobile\//` so it does not run the phone specs at its own viewport;
  `mobile-chrome` (`devices['Pixel 7']`) and `mobile-safari` (`devices['iPhone 13']`) take
  `testMatch: /mobile\//`. WebKit rather than Firefox for the second engine: Playwright's `isMobile`
  is unsupported on Firefox, and the mechanism behind pages-1 (a `backdrop-filter` ancestor becoming
  the containing block for a `fixed` descendant) is exactly the class of behaviour that differs by
  engine. `resolvePort` and the `webServer` block are untouched, so ADR 0014 still holds: one
  server, started by this run, never reused.
- **Annotations.** `test.fail()` plus
  `test.info().annotations.push({ type: 'fixed-by', description: 'R1, #46' })` on the Playwright
  side, `it.fails` with the row ID and the task named in the test title on the Vitest side. Do not use
  `test.skip` or `test.fixme`: a skipped test proves nothing and does not fail when the defect is
  fixed. The annotation text is what the fixing pull request searches for.
- **Hydration.** Every phone and desktop spec reuses the existing wait —
  `await expect(page.getByText('System Boot', { exact: true })).toBeHidden({ timeout: 30_000 })` —
  before any interaction, as `e2e/hero.spec.ts:15` and `e2e/accessibility.spec.ts:259` do. Events
  fired before that are lost, and on routes other than `/` the locator matches nothing and the wait
  resolves at once. The loader is the only hydration marker the page has, so keep it working
  (hero-9's note: it is server-rendered under the story's stacking context and unmounts 600ms after
  hydration, which is why the wait is not vacuous). The one exception is `e2e/served-html.spec.ts`
  (R16): the loader is rendered on `visible={!mounted}` from `useIsHydrated()`
  (`animated-hero/index.tsx:186`, `:195`), so with `test.use({ javaScriptEnabled: false })` it never
  unmounts and that wait would time out. That spec waits for nothing, asserts computed `opacity`
  rather than `toBeVisible()` — the loader sits over the story, so visibility is the wrong
  instrument — and cross-checks the same states in the raw response from `request.get('/')`.
- **Query cost.** Resolve each element once and reuse the handle —
  `const tags = island.getByRole('listitem')`, then iterate — rather than calling
  `getByRole(..., { name })` inside a loop: the accessible name of every candidate is recomputed on
  each call, and in jsdom a GSAP-driven mount is expensive because every tween reads its start value
  through `getComputedStyle`. The accessible-name assertions in `hero-story-names.spec.ts` are the
  one place where the name itself is the subject, so they query by name deliberately.
- **Contrast budget.** Read
  `results.incomplete.find(({ id }) => id === 'color-contrast')?.nodes.length ?? 0` alongside the
  existing `passingNodes` helper and compare it to a recorded per-route, per-scheme budget, with the
  measured values in a comment (`/` at rest: 103 passing against 114 incomplete light, 113 dark).
  Mirror the existing positive control at `e2e/accessibility.spec.ts:377` with a `setContent` page
  whose text sits on a background gradient, which is what makes axe answer `incomplete`, and assert
  the budget comparison fails on it. Keep `test.describe.configure({ retries: 0 })` on every pass.
- **Hero colour assertions.** Axe cannot decide these nodes, so the spec asserts computed style
  instead: read `getComputedStyle(el).color`, reject any alpha below 1, composite the colour over
  the island's own resolved background and compute the WCAG ratio in the spec. Do the same after
  `hover()` and after `focus()`. That is the only form that fails on the shipped hero, and it is why
  the colour rows are a separate spec from the axe gate.
- **Status colour across two routes (R39).** The same instrument, one route apart: read
  `getComputedStyle(el).color` on the featured card's status label on `/` and on the matching `/work`
  card's, in both schemes, and assert the two resolve to one value. Do not pin a hex or a token name —
  the row is about the two routes agreeing, not about which green wins, and #49 may settle it
  either way (see Owner decisions). Axe is the wrong instrument twice over: it reports no violation
  today, and both cards are blurred panels (`featured-work.tsx:67` is `backdrop-blur-md`,
  `work/page.tsx:54` is `backdrop-blur-sm`), which hides their text from its contrast check on the
  HudPanel precedent. Nothing has to be scrolled or hovered, because `color` is read directly and neither card's
  status label is state-dependent (the active/inactive switch at
  `featured-work/metric-counter.tsx:67` is the metric, not the status).
- **Footer copy (R38).** Assert the shape, not the year: `/^© \d{4} Milos Cvetkovic\./` over the
  paragraph's text, which fails today only on the missing `©` (`footer.tsx:72`). The year is frozen at
  build time because the footer is a prerendered server component, so a unit test that pinned a
  literal year would pass in jsdom and say nothing; deciding what that year should be is #49's.
- **Story outline (R15).** No axe rule catches this one — `heading-order` only checks level jumps —
  so the assertion is a role query: `page.getByRole('region', { name: /strategy/i })` and its five
  equivalents, plus each region's first heading. A bare `<section>` maps to `region` only once it has
  an accessible name, so today the query resolves nothing, which is what makes the row RED; after the
  fix it must resolve exactly one element per phase. Assert the heading text against the visible
  phase title, not a hard-coded copy of the closing statement.
- **Routes in one place.** The specs read one list, `apps/web/e2e/routes.ts`, which enumerates the
  six static routes and derives the case studies from `apps/web/src/data/case-studies.ts`, as
  `e2e/console-clean.spec.ts:23` already does for its own list. Consolidating the _source_ side, so
  `sitemap.ts` reads the same module, belongs to #48: this task asserts `sitemap()`'s output
  against the data rather than editing it.
- **SEO over served HTML.** Use `request.get(path)` and parse the returned HTML, not the hydrated
  DOM: what crawlers and link-preview bots read is the server response. `og:image` reachability is a
  second `request.get` of the resolved URL, asserting 200 and an `image/*` content type.

### Traps specific to this repo

- The suite owns port 3210 and never reuses a server, so a run killed part-way leaves an orphan that
  aborts every later run: `lsof -ti tcp:3210 | xargs kill`. A second checkout needs
  `PLAYWRIGHT_PORT=3211`, not a patched config.
- Only an e2e run refreshes `.next-e2e`, and `apps/web/tsconfig.json` compiles the route types in
  it. Adding specs does not change that, but a stale copy makes `pnpm typecheck` disagree with CI
  about routes; clear it with `pnpm --filter web clean`.
- A suite that fails in milliseconds after the webkit addition is a missing browser, not a broken
  spec: run `pnpm --filter web exec playwright install --with-deps webkit` first.
- `test.use` silently ignores an unknown option, and `reducedMotion` is not one of them at test
  level — set it with `page.emulateMedia`, as `e2e/accessibility.spec.ts:246` does, and assert the
  emulation reached the page (the existing gate asserts the `<html>` class for exactly this reason).
- Chromium reports a 404 document as a console error; `e2e/console-clean.spec.ts:73-80` already
  allows that one entry per not-found route, so the dark-scheme pass must reuse the same predicate
  rather than a fresh one.
- Axe types come from `AxeBuilder`, not from `axe-core`, which is not resolvable from `apps/web`;
  follow the `type AxeResults = Awaited<ReturnType<AxeBuilder['analyze']>>` pattern at
  `e2e/accessibility.spec.ts:80-82`.
- Element screenshots scroll the page back and reverse GSAP sections. Capture the baseline
  screenshots top to bottom in one pass.
- The local run serves the dev server and CI the production build. StrictMode double-invocation bugs
  appear only locally, and minified React hydration errors only in CI, so both modes are required
  evidence, not one.
- The in-app browser pane reports React error #418 on every page of the deployed site while headless
  Chromium reports none. Judge console cleanliness with Playwright.
- Vitest's 5s `testTimeout` stays. A phase lifecycle test that genuinely needs longer takes an
  explicit third argument with a comment, as `story-phases.test.tsx` does. New node-only test files
  (`sitemap`, `robots`, the source-literal checks) declare `@vitest-environment node` in a docblock:
  building a jsdom window costs about two seconds per file.

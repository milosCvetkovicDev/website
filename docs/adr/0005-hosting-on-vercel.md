# 0005. Hosting on Vercel

## Status

Superseded by ADR-0016 (corrected 2026-09-12)

No longer applies: "No `vercel.json` is added". See [ADR 0016](0016-vercel-deployment-budget.md).

The decision stands but has not been carried out. As of 2026-09-08 there is no Vercel
project and `miloscvetkovic.dev` is still parked, so everything recorded below describes what
becomes true once the procedure in [docs/runbooks/deploy.md](../runbooks/deploy.md) has been
followed.

## Date

2026-09-08

## Context

`apps/web` is a Next.js 16 App Router site that prerenders completely at build time. The last build
produced 14 prerendered routes: the six pages (`/`, `/about`, `/blog`, `/contact`, `/skills`,
`/work`), three `/work/[slug]` case studies generated by `generateStaticParams` from
`src/data/case-studies.ts`, plus `/sitemap.xml`, `/robots.txt`, `/favicon.ico`, `/_not-found` and
`/_global-error`. There is no `api/` segment and no hand-written `route.ts`, no middleware, no
database and no secrets. The only route handlers are the ones Next generates from the `sitemap.ts`,
`robots.ts` and `favicon.ico` metadata files, and all three prerender at build time.
`apps/web/next.config.ts` carries no options at all.

The only runtime input is `NEXT_PUBLIC_SITE_URL`, read in four places with
`https://miloscvetkovic.dev` as the fallback: `src/app/layout.tsx` (`metadataBase` and Open Graph
`url`), `src/app/sitemap.ts`, `src/app/robots.ts` and `src/components/json-ld.tsx`. Every canonical
URL the site emits therefore derives from a single origin, so the site must be served from one
origin and not from two equally valid hostnames.

The site is not deployed. `miloscvetkovic.dev` still resolves to a Namecheap parking page: apex
`A 162.255.119.232`, `www CNAME parkingpage.namecheap.com`, nameservers `dns1` and
`dns2.registrar-servers.com`. The
[2026-01-27 monorepo design](../plans/2026-01-27-monorepo-design.md) already named Vercel on the
free tier, so this record confirms that choice, fixes the details and states what changes at the
registrar.

## Decision

Host `apps/web` on Vercel.

| Setting                | Value                                                                                                                                                                                                                        |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Vercel projects        | One, for `apps/web`                                                                                                                                                                                                          |
| Git repository         | `github.com/milosCvetkovicDev/website`, through the Vercel GitHub app                                                                                                                                                        |
| Root directory         | `apps/web`                                                                                                                                                                                                                   |
| Framework preset       | Next.js                                                                                                                                                                                                                      |
| Node version           | 22.x, set in the project settings. Vercel does not read `.nvmrc`, and `apps/web/package.json` has no `engines` field, so the repository's pins do not reach the build                                                        |
| Install command        | `pnpm install --frozen-lockfile`, an override on the default, so the build resolves from the committed lockfile                                                                                                              |
| Production deployments | `main`                                                                                                                                                                                                                       |
| Preview deployments    | Every push to a non-production branch, through the Vercel Git integration; the URL is posted to the pull request when one is open                                                                                            |
| Environment variables  | `NEXT_PUBLIC_SITE_URL=https://miloscvetkovic.dev`, for Production and Preview, not Development                                                                                                                               |
| Primary domain         | `miloscvetkovic.dev` (apex), with `www` redirecting to it                                                                                                                                                                    |
| DNS                    | Stays at Namecheap. Enter the apex `A` and `www` `CNAME` values that the project's Domains settings show; at the time of writing those are `A 76.76.21.21` and `CNAME cname.vercel-dns.com`, which Vercel has changed before |

The step-by-step procedure, the exact records to enter, the verification commands and the rollback
path are in [docs/runbooks/deploy.md](../runbooks/deploy.md). This record holds the reasoning; the
runbook holds the operation.

`NEXT_PUBLIC_SITE_URL` is redundant in Production, where the code already falls back to the same
value. It is set so that preview builds emit apex canonical URLs in the metadata, sitemap,
`robots.txt` and JSON-LD rather than a `*.vercel.app` origin.

The apex is primary because the metadata, sitemap, `robots.txt` and JSON-LD all resolve from one
base URL; serving the same pages on `www` as well would publish canonical URLs that disagree with
the address in the browser.

DNS stays at Namecheap rather than moving the nameservers to Vercel. Two record changes are enough
to go live, and undoing them restores the current state; delegating the zone would move every
future record, including mail, onto a provider chosen for a static site.

No `vercel.json` is added. The framework preset supplies the build and output settings, and adding
configuration that only restates defaults gives another file to keep in step with Next.js. The
consequence is that no response headers are set anywhere: `next.config.ts` declares none and there
is no `vercel.json`, so the site ships with only what Vercel sets by default, and with no HSTS, no
CSP, no `X-Content-Type-Options` and no `Referrer-Policy`. For a static site with no forms, cookies
or authentication the exposure is small, but this is the decision to revisit the first time a header
is needed, and the place to add one is `headers()` in `next.config.ts` rather than a new
`vercel.json`.

`apps/playground` is not deployed. It is a local Vite sandbox with no audience, and the
[January design](../plans/2026-01-27-monorepo-design.md)'s line about a playground subdomain is
superseded here.

## Consequences

Everything below follows once the project exists. None of it is true yet.

### Positive

- Almost no build configuration: the Next.js preset detects the app and runs the `build` script in
  `apps/web/package.json` (`next build`). Only two settings depart from the defaults, the install
  command and the Node.js version, and both are set once in the dashboard and recorded in the table
  above and in [docs/runbooks/deploy.md](../runbooks/deploy.md).
- Each pull request gets a preview URL, so a reviewer can open a change alongside the CI results
  from `.github/workflows/ci.yml` instead of building it locally.
- A fully prerendered site fits inside Vercel's Hobby plan, and there is nothing stateful to outgrow
  it. Hobby is for non-commercial use; this is a personal portfolio that sells nothing and collects
  nothing, so it stays inside those terms. If that changes, the thing to revisit is the plan, not
  the host.
- Rollback becomes a matter of selecting an earlier deployment, and the deployment history becomes a
  record of what was live when.

### Trade-offs

- Vendor coupling. `next/image` optimisation and Vercel Analytics are provider features; using them
  makes a later move more than a DNS change. Nothing in the app uses them today.
- Build minutes and bandwidth are shared across the whole Vercel account, so a busy project
  elsewhere on the account can consume the allowance this site depends on.
- The Git integration builds every push to every non-production branch, not only branches with an
  open pull request, so it duplicates some of the work CI already does and draws on that shared
  allowance while doing it.
- Two providers hold part of the setup: Vercel serves the site, Namecheap answers for the zone. A
  DNS change and a hosting change are made in different places.

## Alternatives considered

- **Cloudflare Pages.** Comparable free tier, a stronger network, and DNS could sit with the same
  provider, which would remove the two-provider split listed above. Capability is not the objection:
  a site that prerenders completely can be exported as static output and served with no adapter at
  all. Rejected on framework alignment. Next.js is a Vercel product, so a Next.js release is
  supported on its first-party host the day it ships, whereas anything beyond static output on
  Cloudflare tracks it through `@opennextjs/cloudflare`. Committing to static output now would also
  mean reopening the hosting question the first time a route has to render on request.
- **Netlify.** The closest substitute: comparable free tier, per-pull-request deploy previews, DNS
  could equally stay at Namecheap, and its Next.js support is a first-party runtime rather than an
  adapter, so unlike Cloudflare it is not ruled out on capability. Rejected on the same
  framework-alignment tie-break, and because swapping one host for an equivalent one buys nothing
  here. If Vercel's plan terms or limits stop fitting, this is the first alternative to reopen.
- **GitHub Pages with a static export.** The only option that adds no new vendor, since the
  repository already runs GitHub Actions. Would need `output: 'export'` in `next.config.ts`. The
  metadata routes survive that and emit static files, but on-demand rendering and any future
  `route.ts` do not, and Pages has no per-pull-request preview deployments, which is the reviewing
  habit this project is built around.
- **Self-hosting on Azure Container Apps.** The stack used elsewhere in this workspace, and it would
  keep everything on one cloud. Rejected here: a container image, registry, ingress, certificates
  and their upkeep are out of proportion to 14 prerendered pages, and it costs money where the
  alternative does not.

## Corrections

### 2026-09-12

One clause inside `## Decision` is false about the response headers the site ships with, and it was
false on 2026-09-08 too: Vercel's default already included HSTS. `## Decision` is never rewritten,
so it is annotated here, under [ADR 0012](0012-correcting-accepted-records.md).

**HSTS is set, by Vercel's default**, in `## Decision`. The record reads: "the site ships with only
what Vercel sets by default, and with no HSTS, no CSP, no `X-Content-Type-Options` and no
`Referrer-Policy`". What is true: the site ships with only what Vercel sets by default, and that
default includes HSTS. What was wrong: the clause lists HSTS among the headers that are absent, while
it is one of the headers the platform default supplies. The other three clauses are accurate and are
not corrected, and the surrounding statement that the repository sets no headers of its own is
accurate as well: `apps/web/next.config.ts` declares no `headers()`.

Evidence: `curl -sSI https://miloscvetkovic.dev/ | grep -i strict-transport-security` prints
`strict-transport-security: max-age=63072000`, a two-year max-age the repository sets nowhere. That
it is the platform default rather than a later configuration change follows from that same absence:
no `headers()` in `apps/web/next.config.ts` and no `vercel.json` setting headers, so no commit
between acceptance and the probe could have added it.

This correction changes nothing about the decision it annotates. The place to add a header is still
`headers()` in `next.config.ts`, and the reasoning for adding none was not conditional on the HSTS
clause being right.

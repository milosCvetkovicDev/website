# 0005. Hosting on Vercel

## Status

Accepted

## Date

2026-09-08

## Context

`apps/web` is a Next.js 16 App Router site that prerenders completely at build time. The last
build produced 14 prerendered routes: the six pages (`/`, `/about`, `/blog`, `/contact`, `/skills`,
`/work`), three `/work/[slug]` case studies generated by `generateStaticParams` from
`src/data/case-studies.ts`, plus `/sitemap.xml`, `/robots.txt`, `/favicon.ico`, `/_not-found` and
`/_global-error`. There are no route handlers, no middleware, no database and no secrets.
`apps/web/next.config.ts` carries no options at all.

The only runtime input is `NEXT_PUBLIC_SITE_URL`, read in four places with
`https://miloscvetkovic.dev` as the fallback: `src/app/layout.tsx` (`metadataBase` and Open Graph
`url`), `src/app/sitemap.ts`, `src/app/robots.ts` and `src/components/json-ld.tsx`. Every canonical
URL the site emits therefore derives from a single origin, so the site must be served from one
origin and not from two equally valid hostnames.

The site is not deployed. `miloscvetkovic.dev` still resolves to a Namecheap parking page: apex
`A 162.255.119.232`, `www CNAME parkingpage.namecheap.com`, nameservers `dns1` and
`dns2.registrar-servers.com`. The 2026-01-27 monorepo design already named Vercel on the free tier,
so this record confirms that choice, fixes the details and states what changes at the registrar.

## Decision

Host `apps/web` on Vercel.

| Setting                | Value                                                                      |
| ---------------------- | -------------------------------------------------------------------------- |
| Vercel projects        | One, for `apps/web`                                                        |
| Root directory         | `apps/web`                                                                 |
| Framework preset       | Next.js                                                                    |
| Node version           | 22, matching `.nvmrc` and the `engines.node` field                         |
| Production deployments | `main`                                                                     |
| Preview deployments    | Every pull request, via the Vercel Git integration                         |
| Environment variables  | `NEXT_PUBLIC_SITE_URL` only                                                |
| Primary domain         | `miloscvetkovic.dev` (apex), with `www` redirecting to it                  |
| DNS                    | Stays at Namecheap: apex `A 76.76.21.21`, `www CNAME cname.vercel-dns.com` |

The apex is primary because the metadata, sitemap, `robots.txt` and JSON-LD all resolve from one
base URL; serving the same pages on `www` as well would publish canonical URLs that disagree with
the address in the browser.

DNS stays at Namecheap rather than moving the nameservers to Vercel. Two record changes are enough
to go live, and undoing them restores the current state; delegating the zone would move every
future record, including mail, onto a provider chosen for a static site.

No `vercel.json` is added. The framework preset supplies the build and output settings, and adding
configuration that only restates defaults gives another file to keep in step with Next.js.

`apps/playground` is not deployed. It is a local Vite sandbox with no audience, and the January
design's line about a playground subdomain is superseded here.

## Consequences

### Positive

- Zero build configuration: the Next.js preset detects the app, and `apps/web/package.json` already
  exposes the `build` and `start` scripts it expects.
- Each pull request gets a preview URL, so a reviewer can open a change alongside the CI results
  from `.github/workflows/ci.yml` instead of building it locally.
- A fully prerendered site fits comfortably inside the free tier, and there is nothing stateful to
  outgrow it.
- Rollback is selecting an earlier deployment, and the deployment history is a record of what was
  live when.

### Trade-offs

- Vendor coupling. `next/image` optimisation and Vercel Analytics are provider features; using them
  makes a later move more than a DNS change. Nothing in the app uses them today.
- Build minutes and bandwidth are shared across the whole Vercel account, so a busy project
  elsewhere on the account can consume the allowance this site depends on.
- The Git integration builds on every push to an open pull request, duplicating some of the work CI
  already does.
- Two providers hold part of the setup: Vercel serves the site, Namecheap answers for the zone. A
  DNS change and a hosting change are made in different places.

## Alternatives considered

- **Cloudflare Pages.** Comparable free tier and a stronger network, and DNS could sit with the same
  provider. Its Next.js App Router support runs through an adapter, which is more moving parts than
  a site this simple justifies.
- **Netlify.** Equivalent for the static case. It offers nothing Vercel does not for a Next.js
  build, and Next.js support on its first-party host is the better-trodden path.
- **GitHub Pages with a static export.** Would need `output: 'export'` in `next.config.ts` and
  closes off any future use of server rendering or route handlers, and there are no preview
  deployments per pull request.
- **Self-hosting on Azure Container Apps.** The stack used elsewhere in this workspace, and it would
  keep everything on one cloud. Rejected here: a container image, registry, ingress, certificates
  and their upkeep are out of proportion to 14 prerendered pages, and it costs money where the
  alternative does not.

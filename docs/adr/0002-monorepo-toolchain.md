# 0002. Monorepo toolchain and version pinning

## Status

Superseded by ADR-0018 (corrected 2026-09-13)

[ADR 0018](0018-dependency-update-policy.md) replaces the pin table below and the sentence proposing
`22.x` as the tightening of `engines.node`; the rest of this record still stands, read with the
corrections recorded at the end of it.

## Date

2026-09-08

## Context

One repository holds five workspaces: `apps/web` (the public Next.js 16 site), `apps/playground` (a
Vite sandbox for experiments), and three config packages (`@repo/eslint-config`,
`@repo/prettier-config`, `@repo/typescript-config`). Only `@repo/prettier-config` is wired in today:
the root and `apps/web` depend on it through `workspace:*`. `@repo/eslint-config` and
`@repo/typescript-config` are published in the workspace but referenced by nothing, and
`apps/playground` depends on no shared package at all (see
[ADR 0003](0003-formatting-and-linting-standards.md) for why ESLint sharing is deferred). The apps
do not share runtime code, but they must share one lint config, one formatter, one TypeScript base
and one set of quality gates, otherwise the sandbox slowly stops resembling the site it is meant to
prototype for.

Before this decision the toolchain had drifted in three ways, and all three were silent until
something broke:

- An uncommitted `pnpm-lock.yaml` regenerated by pnpm 10 sat against a committed `package.json`
  still declaring `pnpm@9.15.4` (see the
  [2026-09-08 workspace review](../plans/2026-09-08-repo-hardening-and-launch-design.md)), so a
  fresh install could resolve differently from the lockfile on `main`.
- `engines.node` still allowed Node 20 while all development happened on Node 22, so nothing stopped
  a contributor (or a build machine) from using a runtime nobody tested on.
- Three root scripts (`typecheck`, `lint:fix`, `clean`) invoked Turbo tasks that were not declared
  in `turbo.json`. Running `pnpm typecheck` failed with "Missing tasks in project" rather than type
  checking anything, so the command the project documented, and the one CI would later be built on,
  had never actually run.

The common cause is that the version of a tool, and the list of tasks it can run, were written down
in more than one place and nothing kept those places in agreement.

## Decision

Use **Turborepo 2** (`turbo@^2.10.12`, resolved to 2.10.12 by `pnpm-lock.yaml`) on top of **pnpm 10
workspaces**, with the workspace globs `apps/*` and `packages/*` in `pnpm-workspace.yaml`.

Every root script that fans out to workspaces maps to a task declared in `turbo.json`, and every
task in `turbo.json` is implemented by at least one workspace. `dev:web` and `dev:playground` are
the same `dev` task under `--filter`. `dev`, `build`, `lint`, `lint:fix`, `typecheck` and `clean`
exist in both apps; `test` and `test:e2e` exist only in `apps/web`, because the playground has no
tests, so `pnpm test` and `pnpm test:e2e` currently cover the site alone. The config packages ship
files rather than builds and declare no scripts, which Turbo skips; the failure mode being fixed is
a task declared nowhere, not a task absent from one package. `format`, `format:check` and `prepare`
stay outside Turbo: the first two because Prettier already walks the whole tree in a single pass,
and `prepare` because it installs the git hooks once, at the root.

Pin the toolchain in three places, and let everything else read those pins rather than restate them:

| Pin             | Location                        | Value          |
| --------------- | ------------------------------- | -------------- |
| Node version    | `.nvmrc`                        | `22`           |
| Node range      | `package.json` `engines.node`   | `>=22`         |
| Package manager | `package.json` `packageManager` | `pnpm@10.33.0` |

The two Node entries are not identical. `.nvmrc` names the major used locally and in CI, while
`engines.node` is a floor that refuses anything older and would still admit Node 24 or 25.
Tightening it to `22.x` is the follow-up if a build machine ever resolves it upward.

`.github/workflows/ci.yml` restates neither version: `pnpm/action-setup` takes its version from
`package.json#packageManager`, and `actions/setup-node` uses `node-version-file: .nvmrc`. Vercel
reads `packageManager` and `engines.node` from the same manifest, so a connected project would build
on the same pins; that path is not yet exercised, because the site is not deployed (see
[ADR 0005](0005-hosting-on-vercel.md)).

Type checking is defined per app so that it works on a clean checkout with no prior build:

- `apps/web`: `next typegen && tsc --noEmit`. `next typegen` writes `.next/types/routes.d.ts`, which
  `apps/web/next-env.d.ts` imports directly, so a bare `tsc --noEmit` fails to resolve that module
  before a `next build` has ever run.
- `apps/playground`: `tsc -b`, matching the project-references setup Vite scaffolds.

## Consequences

### Positive

- One command works from the repository root regardless of which app it touches: `pnpm typecheck`,
  `pnpm lint`, `pnpm test`, `pnpm build`. Contributors do not need to know which app owns which
  tool.
- CI cannot drift from local development. The workflow installs the Node and pnpm versions named by
  the repository, so "works on my machine" and "passes CI" describe the same toolchain.
- Turbo caches `build`, `lint`, `typecheck` and `test` by input hash, so unchanged workspaces are
  skipped. `dev`, `lint:fix`, `test:e2e` and `clean` set `cache: false` because their output is not
  a pure function of the inputs; `dev` additionally sets `persistent: true`, and the root `clean`
  script appends `rm -rf node_modules` after the Turbo task.
- `pnpm install --frozen-lockfile` in CI fails loudly if the lockfile and the manifests disagree
  about dependencies. The version drift is caught separately, by `pnpm/action-setup` resolving
  `packageManager` rather than a version typed into the workflow.

### Trade-offs

- The Turbo task list is a second place to edit. Adding a root script means declaring the task in
  `turbo.json` as well, and forgetting one half reproduces the original "Missing tasks in project"
  failure.
- A new app package needs the full script set (`dev`, `build`, `lint`, `lint:fix`, `typecheck`,
  `clean`, and `test`/`test:e2e` if it has tests) or the root commands quietly do less than they
  appear to, as `apps/playground` already demonstrates for `test`.
- Pinning Node to `>=22` means contributors on older runtimes must install Node 22 before anything
  works. This is intentional, but it is friction on first clone.
- `packageManager` only binds locally when Corepack is enabled. A contributor who skips the
  `corepack enable` step in the [README](../../README.md) gets whatever pnpm is on `PATH`, and only
  CI catches the difference.
- `@repo/eslint-config` and `@repo/typescript-config` are workspaces that nothing consumes, so they
  are carried, formatted and installed without being enforced. Wiring or deleting them is a
  follow-up.
- Turbo's cache is local only. There is no remote cache configured, so CI starts cold on every run.

The [2026-01-27 monorepo design](../plans/2026-01-27-monorepo-design.md) is superseded on four
points by this record: pnpm 9 becomes pnpm 10.33, Node 20 becomes Node 22, Next.js 15 becomes
Next.js 16, and the remote Turbo cache it anticipated is not configured. The formatting and linting
standard that rides on these workspaces is [ADR 0003](0003-formatting-and-linting-standards.md), the
gates that run these tasks are [ADR 0004](0004-ci-pipeline-and-quality-gates.md), and the
implementing work is the
[tooling and quality gates plan](../plans/2026-09-08-tooling-and-quality-gates-plan.md).

## Alternatives considered

**Plain pnpm workspaces, no task runner.** `pnpm -r run typecheck` already fans a script out across
the workspace, in topological order of the workspace dependencies, which would have covered most of
what is needed here without a second config file. Rejected because it has no caching and no per-task
ordering: every invocation re-runs every workspace, and the order is fixed to the dependency graph
rather than declared per task. The `dependsOn: ["^build"]` edges on `test` and `typecheck` are a
no-op today, since no config package has a `build` script; they are declared so the ordering already
exists the first time a workspace does. The extra `turbo.json` buys input-hash caching now and
explicit ordering later.

**npm workspaces.** Would remove pnpm from the stack, but loses the content-addressed store and the
strict `node_modules` layout that stops a package importing a dependency it never declared. The
lockfile drift that prompted this ADR is a versioning problem, not a pnpm problem, so switching
package manager would not have fixed it.

**Nx.** Stronger dependency graph, affected-project detection and generators, all of which matter at
a scale this repository does not have: two apps, three config packages, no shared runtime library.
The configuration surface is larger than the problem.

**No monorepo tool, split into separate repositories.** Would end the shared-config problem by
ending the sharing. Rejected because the config packages exist precisely so the sandbox and the site
can stay consistent, and because a single repository keeps one CI pipeline, one lockfile and one
place to review changes.

## Corrections

### 2026-09-12

One sentence inside `## Decision` is false about where Vercel takes the Node version from, and it
was already false on 2026-09-08. `## Decision` is never rewritten, so it is annotated here instead,
under [ADR 0012](0012-correcting-accepted-records.md).

**Where Vercel reads the Node version**, in `## Decision`. The record reads: "Vercel reads
`packageManager` and `engines.node` from the same manifest, so a connected project would build on
the same pins; that path is not yet exercised, because the site is not deployed (see
[ADR 0005](0005-hosting-on-vercel.md))." What is true: Vercel reads neither of the root manifest's
pins. It resolves the Node version from the Root Directory's own `package.json` or, failing that,
from the project setting, and `apps/web/package.json` declares no `engines` field, so the version
comes from the project setting alone, where it is `22.x`. What was wrong: the sentence generalises
the CI mechanism, which really does read the root manifest, to Vercel, which does not read the
repository root when a Root Directory is configured. The clause about the path not being exercised
was true when written and is not corrected: the site was undeployed until 2026-09-09.

Evidence, none of it this record's own assertion: [ADR 0005](0005-hosting-on-vercel.md), accepted the
same day, already states it at `:48` — "Node version | 22.x, set in the project settings. Vercel
does not read `.nvmrc`, and `apps/web/package.json` has no `engines` field, so the repository's
pins do not reach the build"; [docs/runbooks/deploy.md](../runbooks/deploy.md) `:106-109` says the
same and gives the command that sets it,
`vercel project update portfolio --node-version 22.x`; and the live project setting reads back with
`vercel api /v9/projects/<project-id> --raw | jq '{nodeVersion, rootDirectory}'`. Two records
accepted on the same date disagreed, and the false half is the one the runbook written to be executed
contradicts.

### 2026-09-13

The 2026-09-12 entry above over-corrects in two sentences, and two of its citations point at the
wrong lines. It is not edited; this entry quotes and withdraws the parts that are wrong, under
[ADR 0012](0012-correcting-accepted-records.md).

**Vercel does read the root `packageManager`.** The entry reads: "What is true: Vercel reads neither
of the root manifest's pins." It then says the `## Decision` sentence generalises the CI mechanism
"to Vercel, which does not read the repository root when a Root Directory is configured." Both are
withdrawn. What is true: even with the Root Directory set to `apps/web`, Vercel reads the repository
root's `pnpm-lock.yaml` and installs the pnpm version that the root `package.json`'s
`packageManager` field names. Only the Node version bypasses the root manifest, coming from the Root
Directory's own `package.json` or, failing that, from the project setting. The `## Decision`
sentence the earlier entry annotated was therefore half right rather than wrong: it holds for
`packageManager` and fails for `engines.node`. The earlier entry's account of the Node version
stands, and so does its use of [ADR 0005](0005-hosting-on-vercel.md) as evidence for it, although
the quoted row's closing words, "the repository's pins do not reach the build", are too broad in the
same way; this entry corrects only ADR 0002.

**Two citations.** The entry cites [ADR 0005](0005-hosting-on-vercel.md) "at `:48`" and
[docs/runbooks/deploy.md](../runbooks/deploy.md) at "`:106-109`". At 4c02b40, the commit that merged
that entry, the Node version row in ADR 0005 is at `:52` and the runbook paragraph at `:110-113`.

Evidence: the production build of `main` at 4c02b40 on 2026-09-13, read with
`vercel inspect <deployment-url> --logs`, logs "Detected `pnpm-lock.yaml` version 9 generated by
pnpm@10.x from package.json#packageManager pnpm@10.33.0" and "Done in 1.2s using pnpm v10.33.0",
while `apps/web/package.json` declares neither `packageManager` nor `engines`, so the version came
from the root manifest. [ADR 0018](0018-dependency-update-policy.md) records the same behaviour.

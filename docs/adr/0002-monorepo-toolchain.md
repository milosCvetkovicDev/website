# 0002. Monorepo toolchain and version pinning

## Status

Accepted

## Date

2026-09-08

## Context

One repository holds five workspaces: `apps/web` (the public Next.js 16 site), `apps/playground` (a Vite
sandbox for experiments), and three config packages (`@repo/eslint-config`, `@repo/prettier-config`,
`@repo/typescript-config`) that the apps consume through `workspace:*` dependencies. The apps do not share
runtime code, but they must share one lint config, one formatter, one TypeScript base and one set of quality
gates, otherwise the sandbox slowly stops resembling the site it is meant to prototype for.

Before this decision the toolchain had drifted in three ways, and all three were silent until something broke:

- `pnpm-lock.yaml` had been regenerated by pnpm 10 while `package.json` still declared pnpm 9, so a fresh
  install could resolve differently from the committed lockfile.
- `engines.node` still allowed Node 20 while all development happened on Node 22, so nothing stopped a
  contributor (or a build machine) from using a runtime nobody tested on.
- Three root scripts (`typecheck`, `lint:fix`, `clean`) invoked Turbo tasks that were not declared in
  `turbo.json`. Running `pnpm typecheck` failed with "Missing tasks in project" rather than type checking
  anything, so the gate that CI depended on had never actually run.

The common cause is that the version of a tool, and the list of tasks it can run, were written down in more
than one place and nothing kept those places in agreement.

## Decision

Use **Turborepo 2** (`turbo@^2.10.12`) over **pnpm 10 workspaces**, with the workspace globs `apps/*` and
`packages/*` in `pnpm-workspace.yaml`.

Every root script in `package.json` maps to a task declared in `turbo.json`, and every task in `turbo.json` is
implemented by each workspace that can meaningfully run it. `dev`, `build`, `lint`, `lint:fix`, `typecheck`,
`test`, `test:e2e` and `clean` all exist on both sides. The config packages ship files rather than builds and
declare no scripts, which Turbo skips; the failure mode being fixed is a task declared nowhere, not a task
absent from one package. `format` and `format:check` stay outside Turbo because Prettier already walks the
whole tree in a single pass.

Pin the toolchain in three places that agree, and let everything else read those pins rather than restate them:

| Pin             | Location                        | Value          |
| --------------- | ------------------------------- | -------------- |
| Node version    | `.nvmrc`                        | `22`           |
| Node range      | `package.json` `engines.node`   | `>=22`         |
| Package manager | `package.json` `packageManager` | `pnpm@10.33.0` |

`.github/workflows/ci.yml` reads both: `pnpm/action-setup` takes its version from `packageManager`, and
`actions/setup-node` uses `node-version-file: .nvmrc`. Neither version is typed into the workflow. Vercel
resolves the same two fields when the project is connected, so the deployment build uses the pins as well;
that path is not yet exercised, because the site is not deployed.

Type checking is defined per app so that it works on a clean checkout with no prior build:

- `apps/web`: `next typegen && tsc --noEmit`. `next typegen` writes the generated route and PPR types that
  `tsc` needs, which a bare `tsc --noEmit` would otherwise fail on before a `next build` has ever run.
- `apps/playground`: `tsc -b`, matching the project-references setup Vite scaffolds.

## Consequences

### Positive

- One command works from the repository root regardless of which app it touches: `pnpm typecheck`,
  `pnpm lint`, `pnpm test`, `pnpm build`. Contributors do not need to know which app owns which tool.
- CI cannot drift from local development. The workflow installs the Node and pnpm versions named by the
  repository, so "works on my machine" and "passes CI" describe the same toolchain.
- Turbo caches `build`, `lint`, `typecheck` and `test` by input hash, so unchanged workspaces are skipped.
  `dev`, `lint:fix`, `test:e2e` and `clean` set `cache: false` because their output is not a pure function of
  the inputs.
- `pnpm install --frozen-lockfile` in CI fails loudly if the lockfile and manifests disagree, which is the
  exact drift that went unnoticed before.

### Trade-offs

- The Turbo task list is a second place to edit. Adding a root script means declaring the task in
  `turbo.json` as well, and forgetting one half reproduces the original "Missing tasks in project" failure.
- A new app package needs the full script set (`dev`, `build`, `lint`, `lint:fix`, `typecheck`, `test`,
  `clean`) or the root commands quietly do less than they appear to.
- Pinning Node to `>=22` means contributors on older runtimes must install Node 22 before anything works.
  This is intentional, but it is friction on first clone.
- Turbo's cache is local only. There is no remote cache configured, so CI starts cold on every run.

## Alternatives considered

**Plain pnpm workspaces, no task runner.** `pnpm -r run typecheck` already fans a script out across the
workspace, which would have covered most of what is needed here without a second config file. Rejected
because it has no task graph and no caching: `test` could not declare `dependsOn: ["^build"]`, and every run
would redo work that had not changed. The extra `turbo.json` is a small price for an explicit, enforced
ordering.

**npm workspaces.** Would remove pnpm from the stack, but loses the content-addressed store and the strict
`node_modules` layout that stops a package importing a dependency it never declared. The lockfile drift that
prompted this ADR is a versioning problem, not a pnpm problem, so switching package manager would not have
fixed it.

**Nx.** Stronger dependency graph, affected-project detection and generators, all of which matter at a scale
this repository does not have: two apps, three config packages, no shared runtime library. The configuration
surface is larger than the problem.

**No monorepo tool, split into separate repositories.** Would end the shared-config problem by ending the
sharing. Rejected because the config packages exist precisely so the sandbox and the site stay consistent,
and because a single repository keeps one CI pipeline, one lockfile and one place to review changes.
